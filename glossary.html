How to use this glossary: “26-Variable” is the project’s naming convention. The entries include roles, objects, artifacts and procedures; they are not 26 mathematical variables or a complete inventory of every deployment parameter. Each definition separates its purpose from the limits of what it establishes.

The Three Roles: Execution Triad

Human responsibility, the instruction framework and the assistant are separate concepts. They are not necessarily three independently running systems.

ENTRY 01

1. The Architect

Definition
The human engineer or accountable team responsible for the intended change, its review and the decision to execute it.
Use in the workflow
Confirms scope, interprets discovery, reviews configuration and tests, approves consequential actions and assigns operational ownership. Review and execution may be separate roles in an enterprise.
Important boundary
A human approval is effective only when it is informed and occurs on the actual execution path. Being at a keyboard does not itself establish authorization or correct review.
Related language
Engineer; reviewer; operator; change owner. These responsibilities may belong to different people.
↑ Term index
ENTRY 02

2. The State Machine / System Directive

Definition
The project’s structured instruction set for organizing discovery, configuration, verification, diagnostics and handoff across seven phases.
Use in the workflow
Defines requested checkpoints, review criteria, evidence records and diagnostic procedures. In advisory chat, the engineer follows the process while the assistant generates proposals.
Important boundary
A prompt is not an independently enforced controller. Machine-enforced state transitions require a surrounding system with persisted state, authorization checks and restricted execution tools.
Related language
Workflow protocol; prompt framework; procedural checklist. An implemented workflow controller is a separate component.
↑ Term index
ENTRY 03

3. The AI Engine

Definition
The language model and assistant interface used to interpret context, draft configuration, explain behavior and help diagnose failures.
Use in the workflow
Produces reviewable queries, payloads, tests, runbooks and summaries. Distinguishes observed facts from hypotheses and asks for missing information when needed.
Important boundary
Actual access depends on the host, connected tools and credentials. The directive cannot guarantee zero network access, remove existing privileges or make generated output correct.
Related language
LLM; AI assistant. A tool-enabled agent has capabilities that an advisory chat may not have.
↑ Term index
[CATEGORY 02 · ENTRIES 04–08]

The Five Build Coordinates

These intake areas organize a deployment request. They identify context and choices; they do not determine every permission, dependency or operational requirement.

ENTRY 04

4. Identity Core

Definition
Project shorthand for the cloud identity and credential services involved in the selected deployment, such as AWS IAM/STS, Microsoft Entra ID or Google Cloud IAM and federation services.
Use in the workflow
Identifies the relying platform, identity objects, trust configuration and credential exchange relevant to the workload.
Important boundary
The external issuer and the cloud accepting its assertion are different roles. Cloud platforms have different identity models, token formats, policy semantics and logging coverage.
Related language
Cloud IAM services; security token service; relying identity platform. These are not all synonyms for the original issuer.
↑ Term index
ENTRY 05

5. Execution Agent

Definition
Project shorthand for the workload execution environment that needs cloud access: for example a CI job, Kubernetes pod or service process.
Use in the workflow
Supplies the source identity context and runs the operation being tested. Record the platform, job/service account and who can modify its code, configuration and credentials.
Important boundary
A platform, runner, workflow and individual job are distinct objects. A trusted platform name or shared IP range does not establish that a particular workload is authorized.
Related language
Workload; CI job; pod; runner. Specify which object is meant in the current case.
↑ Term index
ENTRY 06

6. Infrastructure State: Existing and New Resources

Earlier project label: Brownfield (Existing) vs. Greenfield (Net-New)

Definition
The current existence and ownership of the resources involved in a change. Brownfield means existing resources; greenfield means newly provisioned resources within the declared scope.
Use in the workflow
Guides discovery, state ownership, existing-resource references, import decisions, change previews, recovery and review of replacement or deletion.
Important boundary
Existing does not necessarily mean production, and new does not mean the entire environment is new. Data/existing references and lifecycle flags have limited scope; other declarations can still change resources.
Related language
Brownfield; greenfield; current estate. Deployment state and infrastructure-as-code state are related but different concepts.
↑ Term index
ENTRY 07

7. Data-Plane Asset

Definition
The resource and operation a workload needs, such as retrieving a secret, reading an object, querying a database or requesting a key-management operation.
Use in the workflow
Defines the intended data action, resource identifier and smallest appropriate permission scope. Specify whether the operation lists metadata, retrieves contents, writes data, signs or decrypts.
Important boundary
Resources and operations are not interchangeable. A key-management service may perform operations without exporting a key. A single resource label does not establish the actual permission boundary.
Related language
Target resource; secret store; bucket; database; cryptographic service. Use the provider’s exact object and action names.
↑ Term index
ENTRY 08

8. IaC Payload and Execution Runbook

Earlier project label: IaC Payload & Terminal Runbook

Definition
The reviewed configuration or API/script artifact and its companion instructions for applying, checking and recovering the intended change.
Use in the workflow
Links inputs, dependencies, target context, change preview, approval, execution, expected observations and recovery to an identifiable revision.
Important boundary
Generating a complete file does not make it validated or safe to execute. Terraform, native templates, CLI commands and SDK scripts have different schemas, state handling and failure behavior.
Related language
Deployment artifact; infrastructure template; script; operational runbook. A runbook is not the same object as the configuration it applies.
↑ Term index
[CATEGORY 03 · ENTRIES 09–18]

Components of the Four Architectural Gates

Boundary, Identity, Federation and Access are review areas used by this project. The ten entries below explain their components; they are not an exhaustive attack model or four universally sequential API calls.

ENTRY 09

9. Cloud Boundary Coordinates

Definition
Identifiers that establish the relevant account, directory, subscription, project, resource hierarchy and location for a deployment.
Use in the workflow
Discover the active context and target resource, then document the actual trust and access relationships. Examples include AWS account IDs, Entra tenant IDs, Azure subscription/resource IDs and Google Cloud project identifiers.
Important boundary
Cross-account, cross-tenant and cross-project access can be legitimate. Shared hierarchy or matching identifiers alone do not establish isolation or authorization. Identifiers are not login secrets, but organizational handling rules still apply.
Related language
Deployment context; account/directory/project identifiers. A logical resource group is not a network perimeter.
↑ Term index
ENTRY 10

10. Non-Human Identity Principal

Definition
The security identity to which access is attributed. Examples include an AWS role session, an Entra service principal or managed identity, and a Google Cloud service account or federated principal.
Use in the workflow
Keep runtime principals distinct from trust configuration and deployment identities. In Entra, distinguish the application client ID, application object ID and service-principal object ID.
Important boundary
An AWS OIDC provider is trust configuration, not the role principal. Entra application and service-principal objects are distinct. Google federation can use direct resource access or service-account impersonation; a service account is not mandatory for every design.
Related language
Workload identity; service principal; role; federated principal. Cloud-specific definitions take precedence over the shorthand.
↑ Term index
ENTRY 11

11. Identity Scope and Interactive Sign-In Settings

Earlier project label: Single-Account / Single-Tenant Isolation & Disabled Browser Redirect URLs

Definition
Provider-specific configuration affecting where an identity can be represented, what it trusts and which interactive application flows are configured.
Use in the workflow
Review tenant/account relationships, external trust, sign-in audience, redirect URIs where relevant, credentials and the people or workloads that can modify them.
Important boundary
Entra single-tenant mode and a blank redirect URI do not establish universal isolation or eliminate phishing. AWS and Google trust restrictions are not equivalent to an Entra redirect setting. Review supported authentication paths separately.
Related language
Trust scope; application audience; headless workload design. These settings are distinct controls, not one universal isolation switch.
↑ Term index
ENTRY 12

12. OpenID Connect and Workload Federation

Definition
OIDC is an identity layer built on OAuth 2.0. Cloud workload federation can use an issuer-signed token as an assertion that a relying service evaluates when exchanging for cloud credentials.
Use in the workflow
Review signature validation, issuer, audience, subject, validity and supported conditions using the relevant platform’s mechanism.
Important boundary
OIDC, workload federation and a cloud token-exchange API are not identical concepts. In Entra federation, api://AzureADTokenExchange is an audience value, not the token endpoint URL. Federation can remove a stored cloud credential from one path without eliminating every credential.
Related language
OIDC assertion; federated identity credential; web-identity role assumption. The source assertion and resulting cloud credential are separate.
↑ Term index
ENTRY 13

13. Subject Claim and Workload Source

Earlier project label: Subject Claim & Code Repository and Branch

Definition
The sub claim identifies a subject in the issuer’s context. Its format can represent a repository/branch, environment, service account or another issuer-defined workload context.
Use in the workflow
Compare the actual assertion format and repository/service-account settings with the relying trust policy. Review issuer, audience and source mutation paths alongside subject conditions.
Important boundary
The subject is not always a branch name, and name casing or numeric IDs alone do not establish secure trust. Exact-match or other condition behavior is platform-specific. Inspect claims safely without posting a reusable assertion or access token.
Related language
Subject condition; source identity; repository/environment context. A GraphQL node ID and numeric REST ID are different identifiers.
↑ Term index
ENTRY 14

14. Short-Lived Cloud Credentials

Earlier project label: 60-Minute Login Token

Definition
Time-limited credentials issued under the selected cloud service’s rules. They may be an access token or, in AWS STS, an access key ID, secret access key and session token.
Use in the workflow
Record requested and actual lifetime, relevant policy settings, renewal, credential storage and the permissions associated with the session.
Important boundary
There is no universal 60-minute ceiling. Source assertion and cloud credential lifetimes can differ. Expiration does not erase a value from memory or logs, and a temporary credential can be stolen while usable.
Related language
Temporary session credentials; access token. Not every credential is a JWT, and credential format is distinct from how it is used.
↑ Term index
ENTRY 15

15. Readiness and Replication Handling

Earlier project label: 30-Second Server Sync Timer

Definition
The checks and bounded retry behavior used when a newly created or updated object is not yet usable by a dependent operation.
Use in the workflow
Classify the actual error, inspect object state and permissions, use supported retries/backoff, and define a timeout and escalation decision.
Important boundary
A fixed 30-second sleep is a possible local workaround, not proof that replication completed or that every 404 is transient. Retrying does not correct the wrong target, missing permission or invalid schema.
Related language
Eventual consistency; readiness probe; retry/backoff. A delay is not an independently verified consistency barrier.
↑ Term index
ENTRY 16

16. Data-Plane Permission Grant

Earlier project label: Data-Plane Role

Definition
A role, policy or binding that permits specific data operations on a resource or resource set.
Use in the workflow
Derive allowed actions and scope from the workload requirement. Inspect direct, inherited and resource-based grants, conditions, alternate credentials and the power to change those controls.
Important boundary
Data-plane access is not necessarily read-only or harmless; it may include write/delete. One narrow grant does not prove that the identity has no other access. A successful read does not prove denial elsewhere.
Related language
IAM/RBAC entitlement; resource binding; effective permissions. A policy statement and the resulting effective access are different things.
↑ Term index
ENTRY 17

17. Broad Management Privileges

Earlier project label: Admin, Owner & Contributor Roles (Blocked Management Roles)

Definition
Administrative or widely scoped permissions that can modify infrastructure, identity configuration, grants or other security-relevant settings.
Use in the workflow
Avoid granting broad privileges merely to clear an error. Distinguish the runtime identity from a deployment principal that may need separately approved, scoped and time-limited administrative operations.
Important boundary
Rejecting a few role names does not prove that control-plane changes are impossible. Inspect actual actions, scope, inherited permissions and indirect escalation paths; similarly named roles across clouds are not equivalent.
Related language
Administrative access; control-plane privileges; over-permissioning. Least privilege is an effective-access assessment, not a role-name blacklist.
↑ Term index
ENTRY 18

18. Authorized Authentication and Role-Assignment Handoff

Earlier project label: Cloud Console / Azure Portal MFA Handoff

Definition
A reviewed change of operator, authentication context or execution method when the current identity cannot complete an approved operation.
Use in the workflow
Diagnose tenant/context, permission, policy, credential and interaction requirements. If a portal or privileged operator is appropriate, record the same target, scope, approval and resulting change.
Important boundary
A 401/403 does not establish that a terminal dropped MFA claims. Portal use and device-code login are not universal fixes or guarantees of required claims. Workload authentication is distinct from a human administrator’s MFA.
Related language
Administrative handoff; approved interactive authentication; role-assignment workflow. This is not permission to bypass a protection.
↑ Term index
[CATEGORY 04 · ENTRIES 19–26]

Verification, Evidence and Diagnostics

These terms describe records and review procedures. An artifact, an executed test and an independently assessed conclusion are different things.

ENTRY 19

19. Identity Architecture Ledger (IAL)

Definition
The project’s baseline record of intended and observed cloud context, identity, trust and access configuration, linked to its evidence and revision.
Use in the workflow
Usually created or updated before behavioral testing, after deployment/read-back. Record provenance, timestamps, unresolved values and later test references without pre-filling runtime success.
Important boundary
A Markdown document is editable. Integrity controls require separate implementation, and even a signed record does not prove every claim in it. A baseline snapshot is not an independent audit.
Related language
identity_architecture_ledger.md; configuration baseline; discovery record. Avoid describing a pre-test snapshot as completed runtime proof.
↑ Term index
ENTRY 20

20. Validation Bridge and Runtime Log Handling

Earlier project label: Validation Bridge & Runtime Log Masking

Definition
The test workload used to exercise the intended identity path, together with safeguards on the output it produces.
Use in the workflow
Capture operation/status evidence and meaningful expected-denial cases. Minimize output; apply platform-supported masking before relevant output and review error/debug paths.
Important boundary
An echo of “success” is not an operation result. Masking redacts supported log matches; it does not erase memory or catch every transformation. GitHub workflow commands are not a universal local-terminal feature.
Related language
Validation workflow; access test; log redaction. Test behavior and output protection need separate checks.
↑ Term index
ENTRY 21

21. Cloud Monitoring Metrics

Earlier project label: Cloud Monitoring Metrics (Total Service API Hits / CloudWatch / Portal Metrics)

Definition
Service-specific aggregate measurements exposed through systems such as CloudWatch, Azure Monitor and Google Cloud Monitoring.
Use in the workflow
Check the actual metric definition, dimensions, time window and aggregation. Use metrics to support diagnosis alongside attributable request and identity evidence.
Important boundary
A request-count spike alone does not prove caller identity, successful content retrieval, zero denials or least privilege. Metric names and collection/ingestion delays vary; no universal 5–20-minute log delay is assumed.
Related language
Request counters; service metrics; operational telemetry. Aggregate metrics are not the same as per-request audit logs.
↑ Term index
ENTRY 22

22. Audit Results Ledger (ARL)

Definition
The project’s assessment record linking defined criteria to observed outcomes, supporting evidence, findings, limitations and reviewer decisions.
Use in the workflow
Record PASS when a criterion is met, FAIL when violated, PENDING when evidence is incomplete and ERROR when the check could not execute. Include scope, revision and observation window.
Important boundary
Do not award every guardrail PASS because one operation worked. A generated report is not certification, insurer acceptance, audit immunity or proof of complete security.
Related language
audit_results_ledger.md; findings report; review record. The authority and scope of a formal audit must be established separately.
↑ Term index
ENTRY 23

23. Telemetry Query and Evidence Artifact

Earlier project label: Standby CloudTrail, KQL & SIEM Telemetry (kql_telemetry.md)

Definition
The query, collection assumptions and result references used to investigate identity events and resource operations for a defined run.
Use in the workflow
Verify enabled collection, source schema, permissions, retention and time window. Retain the executed query version, results and a documented principal/session mapping where correlation is claimed.
Important boundary
A saved query is not a result or an active detector. Time proximity alone is not token identity. Missing fields or events are evidence gaps; a tolerant projection cannot create absent observations.
Related language
kql_telemetry.md; CloudTrail query; KQL query; log review. Cloud-specific engines and table schemas require separate validation.
↑ Term index
ENTRY 24

24. Patch Loop, State Re-Sync and Defect Ledger

Earlier project label: Standard Patch Loop (Iterations 1 to 3), State Re-Sync & Defect & Patch Ledger

Definition
The project’s procedure for recording an isolated defect, evaluating a proposed repair and restoring a coherent, reviewable artifact.
Use in the workflow
Track the error, hypothesis, minimal change, expected/actual result and evidence. Keep a unified artifact plus a diff. Mark a cause or fix verified only when its relevant tests support it.
Important boundary
“State Re-Sync” here means artifact/context consolidation, not authorization to rewrite Terraform state. Whole-file output does not validate the code. A reported successful retry does not necessarily establish the root cause.
Related language
patch_ledger.md; DPL; diagnostic log; reviewed repair. Proposed, reported and verified fixes should remain distinguishable.
↑ Term index
ENTRY 25

25. Diagnostic Escalation and Review Budget

Earlier project label: The 4-Iteration Circuit Breaker & Estimated Probability of Success (X%)

Definition
A chosen limit or trigger for stopping repeated repairs and reassessing the evidence, assumptions, impact and alternatives.
Use in the workflow
The earlier directive’s policy permits three repair attempts and calls for review at the fourth iteration. Escalate earlier for destructive change, privilege expansion or contradictory evidence.
Important boundary
Four is not a scientifically established safety threshold. A prompt-requested halt needs an actual execution gate to be enforced. Do not invent a success percentage without a defined, validated estimation method.
Related language
Retry budget; escalation checkpoint; circuit-breaker policy. A software-enforced circuit breaker is distinct from a chat instruction to stop.
↑ Term index
ENTRY 26

26. Session Review and Versioned Directive Updates

Earlier project label: AI Performance Scorecard & System Directive Compilation

Definition
The close-out process for reviewing actual session events, unresolved findings and candidate improvements to the directive or templates.
Use in the workflow
Count events from records with clear definitions. Review lessons, reproduce fixes, test regressions and release an approved version. Revise or retire obsolete rules when needed.
Important boundary
Process counts are not security-success rates. Packaging an updated prompt is not compiler verification, permanent learning or a guarantee that an error cannot recur.
Related language
Session scorecard; lessons learned; prompt/template release. Preserve version history and the evidence supporting each change.

[ENGINEERING APPENDIX]

Terminology, Models and Evidence

Precise language helps a reviewer follow the work. It does not replace implementation, testing or independent assessment.

Consistent vocabulary

Use a stable project label, then map it to the provider’s actual object or API field. Preserve the differences between an application and a service principal, a workflow and a runner, or a trust policy and a permission grant.

Related words need not be interchangeable. A one-to-one naming rule cannot make distinct technical objects equivalent.

Formal claims need formal scope

Numbered terms and a data-flow diagram do not establish a deterministic or unbypassable system. A formal model needs defined states, inputs, transitions and properties; an operational controller needs enforcement and validation.

This glossary does not claim mathematical proof or conformance to an ISO/IEC/IEEE standard.

Design space versus tested coverage

The earlier matrix multiplies 3 identity cores × 4 agent categories × 2 resource states × 3 asset classes × 3 tooling tracks = 216 option combinations.

The arithmetic describes an abstract selection space. Some choices may be incompatible, require different implementations or remain untested. Publish planned, implemented and tested coverage separately.

Claim, observation and conclusion

Keep intended configuration, read-back observations, test results and reviewer conclusions distinct. Cite the run, revision, source and time window for each assessed result.

A generated ledger, metric spike or confident explanation should support only the conclusion its evidence can establish.

Cross-reference continuity: All 26 entry numbers are retained. Earlier labels are shown where useful, including the former 60-minute credential, 30-second timer and fourth-iteration names. These labels identify earlier project conventions, not universal cloud properties.
