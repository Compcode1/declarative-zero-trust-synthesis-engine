THE BUSINESS SETTING

Protecting the Settings Behind an Automated Report

Imagine a construction company using camera recordings to help managers understand progress across a large building site. Software would examine the recordings and prepare reports. Shared settings would tell that software which site it is working on and what kind of summary to prepare. An unwanted change to those settings could change the software’s behavior.

For this demonstration, we created Company X, a fictional construction-AI business. We assumed its wider system would connect cameras, cloud storage, analysis software and reports for site managers. The lab focused on one useful part of that system: controlling which automated task may publish a settings file and which task may read it.

The assumed business workflow

Camera recordings → private cloud storage → analysis software → a report for a site manager.

The lab built and tested the settings handoff that an analysis service could use. It used harmless sample settings; the camera, analysis and reporting services are the surrounding design assumptions.

The result: Publisher uploaded the selected file. Reader retrieved bytes matching the published sample. AWS refused Reader’s attempt to replace the file, along with the other selected attempts to go beyond each job’s permissions. This establishes a tested separation of publishing and reading authority for the demonstrated handoff.

Why it matters: an attacker who gains control of a reading task should not automatically gain permission to change the settings that other tasks use. Separate identities let engineers assign and test those responsibilities individually.

ADVERSARIAL KILL CHAIN COUNTER ENGINEERING

From an Attacker’s Opportunity to a Tested Restriction

The Adversarial Kill Chain Counter Engineering (AKCCE) system organizes the work around a practical question: if an attacker obtains a workload identity, what could that identity let them reach or change? Here, a workload is an automated task, such as Publisher or Reader. We connect the attacker’s opportunity to an access rule, an actual test and a saved result.

The engineer chooses the scope, reviews changes, executes approved operations and accepts the results. The system directive defines the procedure and required records. AI assistance prepares configurations and tests, examines returned results and proposes corrections. Reviewed instructions, scripts and records make the procedure reusable.

Seven phases keep the engineering work in order

  1. Set the scope. Identify the jobs, the information they need and the access they should not have.
  2. Inspect the starting point. Check the identities, resources and existing access rules before changing them.
  3. Review and deploy the configuration. Prepare the access rules and infrastructure, then check what was applied.
  4. Run the access tests. Try the intended operations and selected operations that should be refused.
  5. Assess the evidence. Match the test results to the AWS responses and relevant activity records.
  6. Hand over the work. Retain the configuration, source revisions, results and supporting references together.
  7. Record the lessons. Preserve problems and verified corrections for review before the next version.

Four gates identify the access conditions to examine

A gate is a named checkpoint in the access configuration. These gates are examined during the relevant phases; they are not four extra project phases.

What each AWS gate checks
GateThe engineering question
Identity provider registrationIs AWS configured to recognize the service supplying the job’s identity? This establishes the provider; the next gate restricts which job may use a role.
Role trustDoes the job meet the required source and branch conditions before AWS issues temporary access? Could it obtain the other job’s role?
Role permissionsWhat may the admitted job read or change? Here, the shared file has separate publishing and reading permissions.
Selected-secret resource policiesWhat access rules are attached to each job’s separate stored secret? We review them alongside the other applicable policies and test the resulting access.

The method and its terminology are described in the seven-phase blueprint, adversarial kill chain and system glossary. The sections below show how that structure was applied in this lab.

RESULT AND NEXT STEPS

What We Built and What Comes Next

Scope: two CI jobs, harmless own-secret fixtures and one shared configuration object. The selected role-admission, secret-access and S3 transfer/denial cases passed. The camera, analysis and report interfaces remain proposed application work.

This lab demonstrated controlled settings delivery between two jobs and retained a reviewable engineering handoff. Next, a small local analysis example could check the file’s format and site, read it without listing other files, and produce a sample result or a clear error. Approving what the publisher writes and keeping older approved settings are separate improvements to design and test.

Engineering lessons and retained responsibilities

One correction was needed in the publisher’s report-reading script. We kept the successful upload and the original failure in the record, then completed only the missing check. The records show one known correction attempt and one recovery workflow for that problem. The number of earlier folder-guidance corrections is unknown. The four-attempt stopping rule was not exercised in this run.

The access tests completed, but the engineer-facing explanations still need work. Steve reported that they were hard to follow and that the expected charts did not appear. Those experience problems remain open; this technical completion does not mark them fixed.

The lab ran using instruction version v2.3.4. The retained handoff includes a proposed v2.3.5 update for review; this lab’s results remain attributed to v2.3.4. The saved evidence also notes dependencies that can change over time. Matching the transferred bytes is not a signature proving who approved the publisher’s content, and matching activity records does not prove those records cannot be altered.
