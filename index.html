INTELLIGENT ARCHITECTURE

In modern cloud engineering, artificial intelligence functions as a probabilistic engine—powerful and fast, but prone to guessing IDs or drifting off-spec. To solve this for Microsoft Entra ID and Azure security deployments, I took that probabilistic engine and tethered it to a master System Directive to make it deterministic. The result is the Zero Trust Interactive State Machine: a disciplined 7-step assembly line that guides the build from real terminal ID lookups through passwordless OIDC code generation and live Azure audit verification.

The architecture produces dependable, passwordless Microsoft Entra ID configurations proven by both 'Before' blueprint ledgers and 'After' live Azure API and KQL verification checks."

The Execution Triad: The Zero Trust Interactive State Machine

Writing complex cloud identity code by hand is slow, but letting an untethered AI generate a whole deployment script at once leads to broken code and security holes. To get the speed of AI without giving up control, the Zero Trust Interactive State Machine divides the work across three distinct roles—The Execution Triad. By separating the human decision-maker from the rulebook and the code generator, the AI can never skip steps or invent unverified settings.

[ROLE: HUMAN OPERATOR & DECISION MAKER]

1. The Architect

The Engineer at the Keyboard. Selects the 5 build options in Step 1, runs lookup commands in the local terminal during Steps 2–5, pastes verified non-secret routing IDs into the chat, approves every gate, and executes the finished code in Azure.

[ROLE: THE SYSTEM DIRECTIVE RULEBOOK]

2. The Interactive State Machine

The Hard Guardrails Inside the Prompt. Locks the AI into one step at a time. Forces read-only lookups for existing Brownfield resources, blocks passwords and wildcards, forbids broad Owner/Contributor roles, and pulls the 3-strike Circuit Breaker on Attempt #4 if an error occurs.

[ROLE: TETHERED CODE GENERATOR]

3. The AI Engine

The Controlled Builder. Instead of spitting out half-baked code prematurely, the AI provides terminal lookup commands during Steps 1–5, locks verified IDs and safety rules into memory, and outputs 100% finished IaC scripts, ledgers, and KQL queries in Step 6.

How the Assembly Line Actually Works (From Intake to Live Proof)

1. Starting the Build & Interactive Back-and-Forth (Steps 1–5 — No Files Output Yet): Every build starts with The Architect pasting the master System Directive into the AI, setting up a clean local folder, and selecting the 5 core build options (Cloud Target, Execution Agent, Brownfield vs. Greenfield State, Target Vault/Database, and IaC Language). Instead of letting the AI immediately spit out a half-baked script full of <INSERT_HERE> placeholders, The State Machine forces an interactive back-and-forth across four verification gates: Cloud Boundary (Step 2), Machine Identity (Step 3), Passwordless OIDC Trust (Step 4), and Single-Vault Permissions (Step 5).

2. Real Terminal Lookups & Built-In Crash Prevention: At each gate, if The Architect doesn't already have the exact Azure or pipeline IDs pasted in, The AI Engine provides the exact terminal lookup commands (az CLI or curl) to pull the real non-secret routing IDs directly from the cloud. Along the way, the System Directive locks in rules that prevent classic deployment crashes: using read-only lookups (data / existing) so existing Brownfield vaults are never overwritten, building an automatic 30-second pause timer (time_sleep) into the plan so Microsoft's servers finish syncing new identities before attaching OIDC rules, and separating role assignments if a local terminal drops interactive Azure MFA popups.

3. Generating the Finished Code, Blueprint & Live Cloud Proof (Step 6): Only after all gates in Steps 1–5 are verified does the interactive back-and-forth end. In Step 6, The AI Engine outputs the 100% finished Terraform, Bicep, or PowerShell script alongside the "Before" blueprint table—the Identity Architecture Ledger (Identity_Access_Ledger.md). The Architect then runs the code from the local terminal. Because a green checkmark in a terminal doesn't prove the cloud is actually secure, the workflow immediately runs the "After" checks: generating the Audit Results Ledger (Audit_Results_Ledger.md) from live Azure APIs and running a KQL Log Query to prove the pipeline logged in with its 60-minute OIDC token and unlocked the target vault with zero HTTP 403 Forbidden errors.

4. The 3-Strike Circuit Breaker & Permanent Prompt Upgrades (Step 7): If a command hits an unexpected error during deployment, the system applies the ReAct (Reasoning and Acting) troubleshooting loop with a hard limit. The AI gets up to 3 attempts to fix a terminal error. On Attempt #4, the Circuit Breaker trips automatically and forbids the AI from generating any more code—stopping endless AI guessing spirals. The Architect and AI isolate the root cause, verify the fix locally, record it in the Defect & Patch Ledger (DPL), and compile that rule permanently into the master System Directive so the machine never repeats the same mistake. For the full row-by-row walkthrough, see the Operational Blueprint & Telemetry and the Pipeline Architecture Breakdown.

Enterprise Guardrails: The 5 Built-In Safety Locks

Global security standards like NIST AI RMF and OWASP Top 10 for LLMs provide valuable frameworks for governing artificial intelligence. Inside the Zero Trust Interactive State Machine, those guidelines are translated into five concrete rules within the master System Directive—protecting against five common edge cases in automated cloud deployments:

1. Secret & Credential Protection (What Goes In vs. What Stays Private)

To write 100% finished code without blank placeholders, non-secret routing addresses (Tenant ID, Subscription ID, Resource Group, and Repo names) are safely pasted into the chat during Steps 1–5. Meanwhile, actual secrets never touch the chat or GitHub: OIDC eliminates client secrets completely, and any personal login token (like a GitHub PAT) is typed invisibly inside your local terminal (read -s).

2. Protecting Existing Infrastructure (Brownfield vs. Greenfield)

When working with cloud infrastructure, ensuring existing resources remain untouched is vital. The State Machine prevents accidental modifications by enforcing read-only lookup mode (data blocks in Terraform or existing in Bicep) for Brownfield environments, and locking a prevent_destroy deletion block onto brand-new Greenfield resources.

3. Enforcing Least Privilege (Single-Vault Data Roles Only)

Assigning broad management permissions like Owner or Contributor to an automation pipeline creates unnecessary risk. The State Machine restricts management roles and grants only a data-plane role (like Key Vault Secrets User) locked to that one specific vault or database ID.

4. Supply Chain Safety (Pinned Provider Versions)

To maintain consistency across deployments, provider and extension versions must remain stable. The System Directive requires every script to lock in exact, verified Microsoft provider version numbers across Terraform, Azure Bicep, and pipeline actions so unexpected package updates never disrupt the build.

5. Hiding Temporary Tokens in Pipeline Logs (Runtime Masking)

Even when using passwordless 60-minute OIDC tokens, pipeline configurations must protect runtime variables from exposure. The State Machine enforces automatic log masking (such as ::add-mask:: in GitHub Actions) so sensitive runtime values are scrubbed before anything prints to the console.

[ADAPTATION 01 : PIPELINE OIDC FORMAT]

Adapting to Any CI/CD or Kubernetes Platform

Each pipeline platform presents a different OIDC return address (Subject Claim) to Microsoft Entra ID. Whether you choose GitHub Actions, Azure DevOps, GitLab CI, or an AKS Kubernetes pod, Step 4 provides the exact lookup commands and formats the exact letter-for-letter OIDC trust rule required by that platform—with zero wildcards allowed.

[ADAPTATION 02 : BROWNFIELD VS. GREENFIELD]

Protecting Existing vs. Brand-New Resources

In Step 2 and Step 3, the machine adapts to whether your cloud resources already exist. For existing Brownfield environments, it uses read-only lookups (data in Terraform or existing in Bicep) so live vaults are never overwritten. For brand-new Greenfield builds, it creates the resources with prevent_destroy deletion locks.

[ADAPTATION 03 : SINGLE-ASSET DATA ROLES]

Matching the Exact Vault or Database Role

When you switch the target asset between Azure Key Vault, a Storage Account, or Cosmos DB, Step 5 automatically switches to the exact data-plane role for that service (such as Key Vault Secrets User or Storage Blob Data Contributor) and locks the permission strictly to that single asset's Resource ID.

[ADAPTATION 04 : MULTI-LANGUAGE & MFA SAFE]

Generating Terraform, Bicep, or PowerShell

In Step 6, the verified architecture is output in your chosen language—Terraform (HCL), Azure Bicep, or PowerShell REST API—complete with a built-in server sync pause timer. And if your Azure policy requires an interactive MFA popup that blocks terminal role assignments, Step 5 cleanly separates the role step so you can finish it in the Azure web portal without the script crashing.
