COMPANY X SCENARIO

Why Company X Needs Shared Settings

Company X is a fictional business that uses camera footage to help site managers review construction progress. Its proposed daily report would show which areas changed, which captures were missing and which findings need a person to review. The analysis service would need agreed settings to produce that report.

We built and tested the part that shares those settings. Two automated tasks (jobs) ran from separate GitHub repositories. The publishing job wrote a harmless sample file to one chosen place in private AWS storage (S3). The reading job received the same 114 bytes. We then checked that the reader could not replace the file, the publisher could not write to another location or read the shared file, and the reader could not list the bucket. AWS denied each of those selected attempts.

The proposed camera-to-report workflow

Camera or site gateway → upload service and private footage storage → analysis service → report application → site manager.

This surrounding workflow is a proposed Company X design. The part implemented here is the settings file and the two jobs that publish and read it. A real analysis application could use that same approach when its connection is built and tested.

How this expands Project 04: the earlier project checked that two jobs received their intended AWS identities and could read their own private settings. Project 09 keeps those checks and adds a file shared between jobs with different permissions: one writes, the other reads. The transfer uses harmless settings, with no footage or personal data.

Completed: 17 November 2026 • instructions used: v2.3.4 • two jobs and one shared settings file. Company X and its wider business workflow are fictional.

The same four security checks (gates) remain: the service that supplies job identities; which job AWS accepts; what that job is allowed to read; and who may read each stored secret. The S3 file permissions add test cases within the existing review, rather than creating a fifth gate. AWS considers all applicable access rules, so we checked actual results instead of assuming two permission statements act as two mandatory locks.

Authorized-publisher risk. The publisher can replace the selected object by design. Matching downloaded bytes and denying consumer writes do not establish publisher intent or independent release approval. Those are separate design decisions.

RESULT AND NEXT STEPS

What We Built and What Comes Next

Scope: two CI jobs, harmless own-secret fixtures and one shared configuration object. The selected role-admission, secret-access and S3 transfer/denial cases passed. The camera, analysis and report interfaces remain proposed application work.

We have demonstrated controlled settings delivery between two jobs. Next, a small local analysis example could check the file’s format and site, read it without listing other files, and produce a sample result or a clear error. Approving what the publisher writes and keeping older approved settings are separate improvements to design and test.

Engineering lessons and retained responsibilities

One correction was needed in the publisher’s report-reading script. We kept the successful upload and the original failure in the record, then completed only the missing check. The records show one known correction attempt and one recovery workflow for that problem. The number of earlier folder-guidance corrections is unknown. The four-attempt stopping rule was not exercised in this run.

The access tests completed, but the engineer-facing explanations still need work. Steve reported that they were hard to follow and that the expected charts did not appear. Those experience problems remain open; this technical completion does not mark them fixed.

The lab ran using instruction version v2.3.4. A proposed v2.3.5 update has been written for review and has not been used in another run. The saved evidence also notes dependencies that can change over time. Matching the transferred bytes is not a signature proving who approved the publisher’s content, and matching activity records does not prove those records cannot be altered.
