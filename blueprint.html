7-Phase Counter-Engineering Blueprint

Human review, deployment evidence and controlled changes across the workload identity lifecycle.

A practical workflow for discovery, reviewed configuration, access testing and operational handoff.

  • Purpose: Make the connection between a machine identity’s trust, permissions, deployment code and evidence easier to review.
  • Operating pattern: The engineer owns execution and acceptance in the advisory setup. The AI drafts artifacts and helps diagnose problems.
  • Scope: This page describes the workflow and its acceptance criteria. Evaluate actual implementations through their published source and execution evidence.

Phase 01: Scope & Baseline Discovery

Reference workflow

Inputs: Start with the intended workload, target resource and accountable engineer.

The Architect

Review & execute

  • Choose the deployment scope: Identify the cloud, workload platform, existing or new infrastructure, target resource and deployment tool. Confirm ownership and the approved execution environment.
  • Confirm current context: Run reviewed read-only queries and check the active account, tenant, subscription or project. Keep credentials out of shared outputs.

The System Directive

Review criteria

  • Record prerequisites: Identify existing assets, state storage, logging needs and the recovery owner. Track missing inputs rather than inventing values.
  • Review information handling: Distinguish routing identifiers from secrets and follow the organization’s data-handling rules. A clean folder helps organization, not host isolation.

The AI Engine

Proposed output

  • Draft discovery commands: Produce cloud-specific lookups and explain which outputs establish the baseline.
  • Prepare the workspace record: Name configuration and evidence artifacts and record assumptions, pending coordinates and the next review action.
Ready to advance: The engineer has confirmed the target context, intended scope and unresolved prerequisites.

Phase 02: Federation Metadata & Trust Design

Reference workflow

Inputs: Use the confirmed boundary and the workload platform’s actual identity settings.

The Architect

Review & execute

  • Inspect the workload identity: Confirm issuer, audience and subject or attribute inputs, including repository, environment, branch or Kubernetes service account where relevant.
  • Review trusted sources: Decide which workload contexts may authenticate and which cases must be rejected.

The System Directive

Review criteria

  • Use the provider’s supported model: Match the configured claim format and conditions. Numeric identifiers, naming rules and trust expressions differ across platforms.
  • Protect the trusted workload: Include repository, runner and dependency protections. A compromised authorized job can satisfy an exact trust condition.

The AI Engine

Proposed output

  • Draft the trust configuration: Use discovered values or explicit IaC dependencies for resources that do not yet exist. Identify assumptions and applicability limits.
  • Prepare authentication tests: Describe the allowed path and meaningful rejected-source cases without printing token values.
Ready to advance: The trust design is reviewed, its inputs are traceable and the accepted and rejected workload cases are defined.

Phase 03: Configuration, Plan Review & Execution

Reference workflow

Inputs: Use the reviewed principal, trust design, target operations and current infrastructure baseline.

The Architect

Review & execute

  • Review the proposed change: Inspect configuration, resolved dependencies and the deployment plan, including permission changes, replacements and deletions.
  • Authorize and execute: Approve the intended artifact and scope, authenticate according to organizational policy and execute through the authorized channel.

The System Directive

Review criteria

  • Check effective access: Separate provisioning authority from workload permissions. Consider inherited grants, resource policies and alternate credentials.
  • Protect state and recovery: Review persistence, locking, backup and deletion safeguards. Handle propagation with bounded readiness checks and diagnose authentication errors from evidence.

The AI Engine

Proposed output

  • Draft configuration and runbook: Produce the selected cloud/tool payload, prerequisites and commands for review. Clearly identify anything that remains unverified.
  • Explain the plan and risks: Summarize intended effects, scope changes and the recovery procedure before the human executes.
Ready to advance: The engineer has reviewed and authorized the change, and the applied configuration and execution result are recorded.

Phase 04: Architecture Baseline & Access Tests

Reference workflow

Inputs: Use the actual deployed configuration and the predefined allowed and denied cases.

The Architect

Review & execute

  • Record the deployed baseline: Save the Identity Architecture Ledger with principal, trust, resource scope, credential settings and configuration revision.
  • Run the validation workload: Exercise required operations and selected denials. Inspect normal, error and artifact output for sensitive data.

The System Directive

Review criteria

  • Classify the test result: Distinguish the expected authorization rejection from syntax, network, credential and service errors. A nonzero exit alone is insufficient.
  • Use attributable observations: Record request outcomes and relevant identity/resource details. Metrics support diagnosis; secret values are unnecessary evidence.

The AI Engine

Proposed output

  • Draft safe validation code: Produce non-sensitive assertions and platform-appropriate output handling. Treat masking as a secondary safeguard.
  • Record what was tested: Connect each result to a run or request reference, and leave delayed or unavailable log checks pending.
Ready to advance: Behavioral results and unexpected errors are recorded; failed tests return to the appropriate design or configuration step.

Phase 05: Evidence Review & Audit Records

Reference workflow

Inputs: Use the deployment baseline, test references and required authentication/resource logs.

The Architect

Review & execute

  • Review the event evidence: Execute the relevant queries, check the principal and operation fields and examine the result within the actual logging coverage.
  • Review outcomes and gaps: Accept or reject results against the agreed criteria. Assign unresolved work and record any explicit risk decision.

The System Directive

Review criteria

  • Keep evidence states distinct: Use PASS, FAIL, PENDING or ERROR for each defined check. A generated template or unexecuted query is not a completed verification.
  • Check provenance and limits: Separate author summaries from raw events and independently validated records. Document uncertain correlation and ingestion gaps.

The AI Engine

Proposed output

  • Draft the audit record: Link observations to evidence, with timestamps, tested scope and limitations. Do not prepopulate success claims.
  • Prepare queries and defect history: Use the actual schema, record prerequisites and consolidate tested fixes and unresolved issues in the DPL.
Ready to advance: Results and gaps are explicit. Pending checks retain their status; release acceptance follows the organization’s defined criteria.

Phase 06: Repository Review & Operational Handoff

Reference workflow

Inputs: Use the reviewed source, dependency locks, evidence records and authorized destination.

The Architect

Review & execute

  • Inspect the publication set: Review staged and tracked files for credentials, state, plans and restricted information. Confirm repository and branch.
  • Synchronize deliberately: Resolve remote differences through the normal review process and record the published and deployed revisions.

The System Directive

Review criteria

  • Protect sensitive artifacts: Apply suitable ignore rules and checks while preserving reproducibility records. Already tracked files and earlier exposure need separate handling.
  • Retain the handoff: Include ownership, recovery, pending work and evidence locations. The number of files depends on the implementation.

The AI Engine

Proposed output

  • Draft a shell-appropriate runbook: Explain synchronization and explicit file selection using the actual repository state.
  • Prepare the handoff summary: List the implementation, test results, limitations and next review tasks for the receiving engineer.
Ready to advance: The intended files and destination are reviewed, synchronization is confirmed and the operating owner has a traceable handoff.

Phase 07: Lessons, Baseline Review & Next Version

Reference workflow

Inputs: Use the recorded defects, results, exceptions and configuration changes from the session.

The Architect

Review & execute

  • Review the session record: Check counts against the underlying entries and assess the value of each proposed workflow change.
  • Approve the next baseline: Review the directive/configuration diff and its tests before adopting a new version. Retain unresolved work and recovery information.

The System Directive

Review criteria

  • Test changes before adoption: A successful local fix may not generalize. Check applicability and contradictions; update or retire obsolete instructions when needed.
  • Keep claims within evidence: Iteration counts are process measures. They are not a security-success rate or a guarantee against future regressions.

The AI Engine

Proposed output

  • Draft the lessons and update: Connect each proposed change to the observed defect, tested resolution and remaining limits.
  • Produce a complete reviewable version: Provide the agreed artifacts and revision history without presenting untested rules as established controls.
Ready to advance: The next version is reviewed and saved, while unresolved risks and follow-up checks remain visible.

Troubleshooting Across All Phases

1. Preserve the Baseline

Record the error, relevant non-sensitive output, artifact revision and current state. Separate observed facts from the proposed cause before changing anything.

2. Test a Bounded Change

Review one hypothesis and its proposed change. Record the test and result, retain the defect history and recheck any affected trust or permission boundary.

3. Reassess or Recover

Use a chosen retry budget and stop earlier when evidence or risk warrants it. The original fourth-attempt halt is a review policy, not a proven optimal threshold. The engineer chooses the next path.

After a patch. Save the resulting configuration and diff, record the tested scope and resume from a known checkpoint. Any temporary exception needs an owner, scope and restoration criteria; a weakened control is not evidence that its intended protection works.

Six-Layer Operational Blueprint

A documentation view connecting governance, cloud controls and operational evidence.

The layers organize the design. The implementation must establish which controls exist and where they are enforced; drawing a layer does not deploy it.

[LAYER 1]

Evidence & Governance

Discover and Check

Use authoritative APIs and observations to challenge assumptions. ReAct research informs the observation/action pattern; its benchmark results do not establish universal reliability.

Assign Responsibility

Name the owner of scope, approval, execution and acceptance. Human oversight should match the consequences and actual deployment mode.

Limit Authority

Constrain credentials, tools and resource access. External permission and approval controls are required when the assistant can perform state-changing actions.

Review Repeated Failure

Choose a troubleshooting budget and a recovery path. Use observed error changes to explain options rather than inventing success probabilities.
  • ReAct research
  • OWASP excessive agency
  • NIST human–AI roles
  • Terraform lifecycle limits
[LAYER 2]

Five Configuration Guardrails

Credential Handling

Avoid sharing credentials with the model. Review inputs, logs and artifacts against the organization’s data-handling rules.

Asset & State Protection

Inspect planned changes, references/imports, deletion safeguards and state persistence. Each mechanism has a defined scope.

Least-Privilege Access

Grant required operations on necessary resources, then inspect effective permissions and test relevant denials.

Dependency & Schema Review

Use reviewed dependencies, locks and supported schemas. Verify actual resolved artifacts instead of relying on version labels alone.

Safe Validation Output

Avoid printing tokens and secret values. Apply platform-supported redaction and inspect error paths and retained artifacts.
[LAYER 3]

The Execution Triad

The Architect

Defines scope, reviews artifacts, executes approved actions and accepts the outcome. Owns risk decisions and the recovery path.

The System Directive

Defines the conversation sequence, expected evidence and review criteria. In chat it is an instruction set, not an independent supervisor.

The AI Engine

Drafts discovery commands, configuration, tests and diagnostic explanations. Its actual tools and credentials determine its execution authority.
[LAYER 4]

Four Architectural Gates

1. Boundary

Confirm the target account, tenant, subscription or project, approved relationships and the resource’s actual deployment context.

2. Identity

Identify the workload principal, ownership and alternate credential paths. Prefer suitable managed identity or federation over new persistent workload secrets.

3. Federation

Review issuer, audience, subject or attribute conditions and source-workload protections. Match the current provider configuration.

4. Authorization

Review required operations, resource scope and all effective grants. Protect provisioning authority separately from workload access.
Dependency order. The selected cloud and tool determine the actual resource graph. Existing and new assets have different prerequisites; these four review gates are not a universal four-command deployment sequence.
[LAYER 5]

Artifacts, Results & Handoff

Five artifact groups; actual file counts and formats depend on the implementation.
Artifact Group Purpose Evidence Rule
Configuration & runbook Reviewed code, dependencies, plan and execution instructions. Record the deployed revision and actual execution result.
Identity Architecture Ledger Principal, trust conditions, scope and credential settings. Tie the baseline to discovered or deployed objects.
Audit Results Ledger Defined checks, outcomes, references and limitations. Use an outcome supported by the evidence for that check.
Telemetry queries & results Provider-specific collection and investigation handoff. Distinguish query code from executed results and active monitoring.
Defect & Patch Ledger Symptoms, tested changes, exceptions and open work. Separate hypotheses from confirmed causes and tested resolutions.
PASS: defined check satisfied FAIL: expected property not met PENDING: evidence incomplete ERROR: test could not determine result
Scope of a result. A passing check applies to its tested conditions. A Markdown ledger organizes records; signed integrity, independent attestation and regulatory acceptance require their own evidence and processes.
[LAYER 6]

Diagnostics & Reviewed Improvement

Retain the Checkpoint

Persist the current configuration, evidence references and open issues so the next session can recover context.

Count Recorded Events

Derive attempts and deviations from the defect record. Describe these as process measures, with clear definitions.

Review the Lesson

Check whether a fix generalizes and whether it conflicts with existing instructions or cloud-specific behavior.

Adopt a Tested Version

Review the complete proposed change, run relevant checks and retain its revision and recovery procedure.

[OPERATING MODE & ENFORCEMENT]

Human-Governed Assistance with Explicit Execution Authority

Describe the installation by its actual capabilities and controls.

The advisory pattern described here keeps cloud execution with the engineer. Adding tools or pipeline execution changes that boundary. An autonomy-level label is useful only when its taxonomy, scope and assessment are defined.

Advisory Chat

The assistant proposes code and commands. The engineer holds cloud credentials and performs the actions. Prompt checkpoints support the review procedure.

Tool-Enabled Assistant

Tools may read or change external systems. The integration must restrict capabilities and credentials and enforce any required approval at the execution boundary.

Pipeline-Controlled Execution

A runner executes a reviewed artifact through configured pipeline permissions and approvals. Its controls and records must bind execution to the intended revision and scope.

Implementation distinction. The latter two cards describe integration patterns that need their own controls and validation. The prompt and this page do not create those controls. A model’s statement that it has no tools or has received approval is not an independently enforced boundary.
