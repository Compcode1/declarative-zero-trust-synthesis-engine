[THREAT MODEL :: WORKLOAD IDENTITY & CLOUD ACCESS]

Follow the Attack Path Through Each Trust Boundary

Machine identity security starts with an adversarial question: if a workstation, build job or credential is compromised, which identity can the attacker use and what can that identity do? AKCCE connects those questions to trust configuration, resource permissions and deployment evidence.

This page organizes the analysis into seven review areas. Real incidents can enter at different points, combine several weaknesses or involve dependencies outside this model. Review the selected environment rather than assuming that a single sequence describes every attack.

The aim is to prevent unintended authentication, limit the impact of a compromised authorized workload and retain useful evidence for detection and recovery. The System Directive guides the review; deployed cloud policies and execution controls provide enforcement.

Define the Intended Workload

Identify the owner, execution platform, issuer, principal, target resources and required operations. Record intended cross-account or cross-tenant relationships.

State the Attacker’s Starting Access

Distinguish access to a log, control of an untrusted branch, compromise of an authorized runner and access to identity-administration permissions.

Choose Testable Properties

Specify which sources must be rejected, which operations must be denied and what evidence will establish the result. Record assumptions and untested dependencies.

Using the References

MITRE ATT&CK describes adversary behaviors; OWASP and provider guidance help identify risks and controls. These references support individual review topics. They do not establish that AKCCE is exhaustive, certified or guaranteed to prevent an incident.
[ILLUSTRATIVE PATHS :: DIFFERENT STARTING POINTS]

Three Ways an Identity Boundary Can Be Crossed

1. Exposed Credential

  1. A credential is recoverable from a file, log or history.
  2. It remains usable under the applicable conditions.
  3. Its permissions allow a cloud operation.

Review credential handling, expiry, access scope and the response to exposure.

2. Compromised Trusted Job

  1. An attacker controls code or a dependency in an authorized job.
  2. The job presents claims that satisfy the trust policy.
  3. The resulting session uses its allowed access.

Review repository, dependency and runner controls alongside OIDC trust.

3. Identity Configuration Change

  1. An attacker obtains sufficient administrative authority.
  2. Trust, credentials or permissions are changed.
  3. The changed configuration permits additional access.

Protect identity administration and monitor changes to the approved baseline.

REVIEW AREA 01 PHASE 1 / GATE 1

Workspace Credentials & Deployment Context

[ATTACKER OBJECTIVE & PREREQUISITES]

How This Path Can Become Usable

An attacker who can read an engineering workstation, runner or shared project directory may recover credentials from history, files or cached sessions. A separate operational risk is applying a valid configuration to the wrong account or production resource.

[TRUST BOUNDARY]

What to Inspect

  • Credential material: Bootstrap tokens, access keys and cached sessions that can authenticate a caller.
  • Routing identifiers: Account, tenant, subscription and project IDs that identify a destination but do not authenticate an attacker by themselves.
  • Execution context: The current user or principal, target environment and deployment state.
[SUPPORTING REFERENCES]

Relevant Behaviors & Guidance

  • MITRE ATT&CK: Shell History (T1552.003): Documents recovery of credentials from command history on compromised systems.
    Read the source →
  • OWASP NHI2:2025 — Secret Leakage: Covers exposure of non-human identity credentials during development and operations.
    Read the source →
[DEFENSIVE RESPONSE]

Controls & Verification

  • Discover the context: Resolve the active principal and target boundary with read-only queries before generating changes.
  • Keep credentials out of artifacts: Use an approved input or credential mechanism and inspect scripts, logs and staged files.
  • Protect the execution environment: Assess host controls, session persistence and state storage for local terminals or cloud shells.

Defensive test: Confirm the intended deployment context and inspect credential-handling paths using safe test data. Retain evidence without publishing a live credential.

Remaining dependency: Endpoint compromise can expose credentials or an active session regardless of whether the project folder is new.

REVIEW AREA 02 PHASE 2 / GATE 3

Unintended Workloads Accepted by Federation Trust

[ATTACKER OBJECTIVE & PREREQUISITES]

How This Path Can Become Usable

A cloud provider can accept a valid, signed token from an unintended workload when trust conditions are too broad or incorrectly configured. This can be misuse of a legitimately issued token rather than cryptographic token forgery.

[TRUST BOUNDARY]

What to Inspect

  • Issuer & audience: The accepted token source and intended recipient for the chosen exchange mechanism.
  • Subject & attributes: Repository, branch, environment, service account or other provider-supported conditions.
  • Source protections: The controls governing who may alter or execute the workload that satisfies those conditions.
[SUPPORTING REFERENCES]

Relevant Behaviors & Guidance

  • OWASP NHI6:2025 — Insecure Cloud Deployment Configurations: Includes token-validation and claim-condition weaknesses in workload federation.
    Read the source →
  • GitHub OIDC reference: Documents claim formats and trust inputs for GitHub Actions.
    Read the source →
  • Microsoft Entra federation considerations: Describes exact claim matching, limits and propagation considerations for supported Entra federation configurations.
    Read the source →
[DEFENSIVE RESPONSE]

Controls & Verification

  • Inspect actual claim settings: Discover the current issuer and claim format, including immutable identifiers where supported and configured.
  • Restrict accepted workloads: Use exact matching or intentionally bounded provider-specific conditions. Review fork, branch and environment behavior explicitly.
  • Handle errors without widening trust: Check claim mismatches, dependencies and propagation. Use bounded readiness checks rather than assuming a fixed sleep guarantees replication.

Defensive test: Verify the intended authentication and selected rejected-source, audience or subject cases in an authorized test environment. Record the actual rejection reason.

Remaining dependency: A compromised job that already satisfies the intended trust conditions may still obtain its assigned session.

REVIEW AREA 03 PHASE 3 / GATES 2 & 4

Excessive Access & Identity Administration Abuse

[ATTACKER OBJECTIVE & PREREQUISITES]

How This Path Can Become Usable

After compromising a workload or administrative identity, an attacker may misuse its permissions or change other identities to gain access. Review both direct data access and the ability to change roles, credentials, consent or trust.

[TRUST BOUNDARY]

What to Inspect

  • Effective permissions: All applicable identity policies, inherited roles, resource policies and impersonation paths.
  • Trust relationships: Approved account and tenant relationships, application permissions and consent. Multi-tenant operation alone is not a vulnerability.
  • Provisioning authority: The privileged identity that can create or modify workloads, distinct from the workload’s runtime identity.
[SUPPORTING REFERENCES]

Relevant Behaviors & Guidance

  • MITRE ATT&CK: Additional Cloud Roles (T1098.003): Describes persistence and privilege escalation through changes to cloud roles or permissions.
    Read the source →
  • AWS IAM policy evaluation: Explains how applicable policy types determine access.
    Read the source →
  • Microsoft’s January 2024 Midnight Blizzard analysis: Describes abuse of OAuth applications and elevated application permissions after initial account compromise.
    Read the source →
[DEFENSIVE RESPONSE]

Controls & Verification

  • Scope the workload to its task: Select required operations and resource scope; avoid broad administrative roles as a shortcut for data access.
  • Protect identity administration: Limit who can change trust, credentials, permissions and consent. Monitor those changes separately from ordinary workload reads.
  • Review proposed changes: Inspect replacements, deletions and new grants. Check alternate credentials and inherited permissions before accepting the result.

Defensive test: Exercise required operations and relevant denied operations, including unnecessary writes or administration. Review the policy baseline and authorized cross-boundary access.

Remaining dependency: A narrow new grant does not remove other grants. Role names, application settings or blank redirect URLs alone do not establish an effective access boundary.

REVIEW AREA 04 PHASE 4 / VALIDATION

Tokens & Secrets Exposed Through Runtime Output

[ATTACKER OBJECTIVE & PREREQUISITES]

How This Path Can Become Usable

A caller with access to job logs or artifacts may recover a printed token or secret. A short-lived credential can still be useful while valid; the impact depends on its permissions and other enforced conditions.

[TRUST BOUNDARY]

What to Inspect

  • Output channels: Standard output, errors, shell tracing, debug logs and uploaded artifacts.
  • Credential lifetime: The actual token or session type, expiry, renewal behavior and available revocation mechanisms.
  • Validation design: Whether a test demonstrates access without exposing the returned sensitive value.
[SUPPORTING REFERENCES]

Relevant Behaviors & Guidance

  • GitHub Actions secure use: Explains output risks, least privilege and limitations of automatic secret redaction.
    Read the source →
  • GitHub workflow masking: Documents masking values in logs; it does not describe erasing process memory.
    Read the source →
[DEFENSIVE RESPONSE]

Controls & Verification

  • Minimize sensitive output: Report non-sensitive assertions and request outcomes. Keep tracing and verbose credential output controlled.
  • Use platform-supported redaction: Register sensitive values before possible output and inspect transformed values and error paths.
  • Prepare exposure response: Define who revokes or rotates credentials, investigates use and handles exposed logs or artifacts.

Defensive test: Review successful and failed validation logs and retained artifacts using safe test values. Record the caller, operation and result without publishing a secret.

Remaining dependency: Log masking does not protect a compromised process or make every transformed value safe to print. Credential limits depend on the deployed mechanism.

REVIEW AREA 05 PHASE 5 / EVIDENCE REVIEW

Missing Evidence & Deliberate Logging Changes

[ATTACKER OBJECTIVE & PREREQUISITES]

How This Path Can Become Usable

An attacker may benefit from missing audit coverage or, with sufficient permissions, disable or modify logging. Ordinary ingestion delay is a separate operational condition. Neither has a universal duration across cloud platforms.

[TRUST BOUNDARY]

What to Inspect

  • Event coverage: Authentication, resource operations and security-configuration changes needed for the defined investigation.
  • Logging control plane: Who can change collection, destinations, retention or access to audit records.
  • Evidence quality: Fields that identify the principal, resource, operation, time and outcome, with correlation limits recorded.
[SUPPORTING REFERENCES]

Relevant Behaviors & Guidance

  • MITRE ATT&CK: Disable or Modify Cloud Log (T1685.002): Describes deliberate changes to cloud logging by an adversary with sufficient permissions.
    Read the source →
  • OWASP CI/CD: Insufficient Logging and Visibility (CICD-SEC-10): Identifies inadequate visibility in the software delivery environment.
    Read the source →
[DEFENSIVE RESPONSE]

Controls & Verification

  • Define and protect logging: Confirm required events are enabled and retained; restrict logging changes and monitor collection health.
  • Execute the audit queries: Use actual schemas and supported identifiers to examine the tested activity. Keep unexecuted checks pending.
  • Report evidence-linked outcomes: Use PASS, FAIL, PENDING or ERROR based on observations, with timestamps and source references.

Defensive test: Generate a controlled test operation and confirm its expected events reach the intended destination. Review logging-change permissions and relevant monitoring behavior.

Remaining dependency: An aggregate API-hit spike does not attribute a request to one identity or establish zero denials. A saved query is not a running detector.

REVIEW AREA 06 PHASE 6 / HANDOFF

Sensitive Deployment Artifacts & Repository Changes

[ATTACKER OBJECTIVE & PREREQUISITES]

How This Path Can Become Usable

Repository access can expose credentials and sensitive deployment details committed in state, plan or environment files. Unreviewed configuration or workflow changes can also alter the next deployment’s security behavior.

[TRUST BOUNDARY]

What to Inspect

  • Deployment artifacts: State, plans, backups and configuration values that may contain secrets or sensitive metadata.
  • Repository access: Who can read history, change workflows or approve configuration changes.
  • Version traceability: The relationship between reviewed source, resolved dependencies and the deployed revision.
[SUPPORTING REFERENCES]

Relevant Behaviors & Guidance

  • HashiCorp: Manage sensitive data: Explains sensitive values in Terraform state and plan files and options for protecting them.
    Read the source →
  • MITRE ATT&CK: Code Repositories (T1213.003): Describes collecting valuable information from code repositories.
    Read the source →
  • GitHub ignore rules: Explains that already tracked files need separate handling.
    Read the source →
[DEFENSIVE RESPONSE]

Controls & Verification

  • Protect persistent state: Use approved storage with appropriate access controls, encryption, locking and recovery.
  • Review the staged diff: Select files explicitly, inspect tracked artifacts and run appropriate secret checks. Retain dependency lock files needed for reproducibility.
  • Review synchronization and publication: Check the target repository, branch and remote differences. Use the organization’s review and branch-protection process.

Defensive test: Inspect tracked and staged files, verify the intended commit and record the deployed revision. Treat discovered credential exposure through the incident process.

Remaining dependency: Ignore rules do not remove earlier commits or prevent every deliberate staging action. Pulling changes does not guarantee a conflict-free merge.

REVIEW AREA 07 ALL PHASES / PHASE 7

Configuration Drift & Unsafe AI-Assisted Changes

[ATTACKER OBJECTIVE & PREREQUISITES]

How This Path Can Become Usable

Previously reviewed trust and permissions can change as workloads, dependencies and administrators change. Incorrect AI-generated patches or unreviewed workarounds may introduce new access paths. This is a change-management risk that can enable attacks, rather than a required final attacker stage.

[TRUST BOUNDARY]

What to Inspect

  • Approved baseline: The current trust, effective permissions, credentials and relevant policy exceptions.
  • Troubleshooting record: Observed errors, tested fixes, unresolved issues and confidence in each proposed cause.
  • Assistant authority: The tools, credentials and execution permissions actually available to the AI-assisted workflow.
[SUPPORTING REFERENCES]

Relevant Behaviors & Guidance

  • NIST AI Risk Management Framework: Provides voluntary guidance for managing AI risk, oversight and accountability.
    Read the source →
  • OWASP LLM06:2025 — Excessive Agency: Addresses excessive functionality, permissions and autonomy in AI systems.
    Read the source →
[DEFENSIVE RESPONSE]

Controls & Verification

  • Recheck current state: Compare live configuration with the reviewed baseline, including new credentials and permission changes.
  • Bound the patch loop: Use a defined retry budget, record the evidence and request an engineer-led reassessment when progress stalls.
  • Review lessons before adoption: Test workflow or directive changes, check for contradictions and retain a recovery path. Enforce automated execution limits outside the prompt.

Defensive test: Run regression checks after changes, review the configuration diff and verify ownership and recovery procedures. Persist unresolved work for the next session.

Remaining dependency: A longer prompt, a complete-file response or a chosen fourth-attempt halt does not establish model determinism or prevent every regression.

[SUMMARY :: CONDITIONS, CONTROLS & TESTS]

Map Each Exposure to a Defensive Check

Review the selected environment and retain the actual result of each test.
Review Area Attacker Prerequisite Defensive Response Verification
1. Workspace & credentials Read access to a host, session or artifact containing usable credentials. Context discovery, credential hygiene and approved execution environment. Confirm the intended deployment context and inspect credential-handling paths using safe test data. Retain evidence without publishing a live credential.
2. Federation trust Ability to obtain a token whose claims satisfy an overly broad or incorrect trust policy. Narrow trust conditions, current claim discovery and source-workload protections. Verify the intended authentication and selected rejected-source, audience or subject cases in an authorized test environment. Record the actual rejection reason.
3. Permissions & administration A usable identity with excessive permissions or authority to modify access configuration. Effective-permission analysis, administrative separation and reviewed changes. Exercise required operations and relevant denied operations, including unnecessary writes or administration. Review the policy baseline and authorized cross-boundary access.
4. Runtime output Read access to an output channel that contains a still-usable token or secret. Minimal output, supported redaction and credential-exposure response. Review successful and failed validation logs and retained artifacts using safe test values. Record the caller, operation and result without publishing a secret.
5. Visibility & audit Missing collection or review, or permission to impair the logging configuration. Protected logging, reviewed query results and honest evidence status. Generate a controlled test operation and confirm its expected events reach the intended destination. Review logging-change permissions and relevant monitoring behavior.
6. State & repositories Read access to exposed artifacts, or write authority over security-relevant source or workflows. Protected state, controlled publication and versioned change review. Inspect tracked and staged files, verify the intended commit and record the deployed revision. Treat discovered credential exposure through the incident process.
7. Drift & AI changes Authority or opportunity to change the reviewed baseline without adequate verification. Current-state checks, bounded diagnostics and tested baseline updates. Run regression checks after changes, review the configuration diff and verify ownership and recovery procedures. Persist unresolved work for the next session.

Expand the Model as the Environment Changes

Include the issuer, runner, source repository, dependencies, identity administration and recovery process in the assessment. Software vulnerabilities, compromised trusted components, alternate credentials and organizational changes can create paths outside these seven categories. The value of the model is a reviewable connection between a risk, its control and its evidence.
