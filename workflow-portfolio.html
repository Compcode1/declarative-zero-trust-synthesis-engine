[REVIEW METHOD]

From Working Example to Assessable Evidence

1. Link the artifact

Identify the source revision, resolved dependencies, intended environment, reviewed change and actual run. A generated payload is a proposal until executed and checked.

2. Test the boundary

Separate successful authentication from authorization. Test the intended operation and meaningful denied cases, identifying the principal, target and actual outcome.

3. Record the limits

Retain attributable service evidence, exceptions, final policy state and review decisions. A metric spike or a generated PASS label does not establish the whole security posture.

Work described in the record

  • Identifier discovery: The record describes extracting numeric user and repository IDs from REST API responses. Numeric IDs are distinct from GraphQL node IDs.
  • Trust construction: The shown subject combines names, IDs and a branch reference. Correctness depends on the assertion format configured for that repository.
  • Outcome report: The engineer reports deployment success and a Key Vault metric observation. The underlying signed assertion and complete workflow result are not attached.

Engineering lesson

Review the actual repository OIDC settings, issuer, audience, subject and lifecycle changes together. Numeric identifiers can strengthen identity binding without making the entire connection unbreakable.

Evidence and limitations · Project 08
