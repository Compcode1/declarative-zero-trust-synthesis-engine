Machine identity security depends on the details: which workload can authenticate, how it obtains a credential, what that credential authorizes and what evidence confirms the result. This project brings those decisions into a structured engineering workflow.

Adversarial Kill-Chain Counter-Engineering™ combines attacker-informed analysis, infrastructure as code and AI assistance under human execution authority. It focuses on practical configuration risks across federation, permissions, deployment state and validation.

The System Directive guides the work from live discovery to reviewed configuration and retained evidence. Cloud IAM policies enforce access; engineers assess the configuration and test whether it behaves as intended.

[PART 01 :: MISSION & ENGINEERING METHOD]

Make Machine Identity Configuration Reviewable, Repeatable & Testable

The objective is to reduce preventable identity misconfiguration by connecting threat analysis to deployment code, explicit human decisions and retained evidence.
  • Attack-path analysis: Examine how a workload obtains credentials, which trust conditions admit it, what permissions it receives and how those permissions could be abused.
  • Live discovery: Resolve deployment coordinates and existing objects from authoritative APIs. Record the source and context instead of asking the model to invent missing values.
  • Human-governed changes: Review the configuration and its expected effect before execution. Keep deployment authority with the engineer in the advisory workflow.
  • Evidence-based validation: Record successful allowed operations, expected denials and relevant audit events. Leave checks pending when the required evidence is unavailable.
  • Reviewed improvement: Use the Defect & Patch Ledger to propose tested changes to the workflow, rather than treating every workaround as a permanent security rule.

1. Attacker-Informed Configuration

  • Concrete failure modes: Overly broad trust, persistent workload credentials, excessive resource access, exposed outputs and unmanaged deployment state are practical review targets.
  • Defined threat model: Document the workload, trusted issuer, repository or runtime, target resource and excluded scenarios. Cloud identity is an open operational environment, with dependencies beyond a single pipeline.
  • Measured outcomes: A successful test establishes the observed behavior under its recorded conditions. It does not establish that every attack path has been removed.

2. A Shared Engineering Vocabulary

  • Consistent terms: The 26-Variable System Glossary gives the human and AI a shared vocabulary for the architecture.
  • Explicit dependencies: Record which outputs become inputs to the next step, along with prerequisites and evidence needed to advance.
  • Practical purpose: Naming and sequencing improve clarity and traceability. Their value is assessed through reviews and tests, without assigning unsupported reliability percentages.

[PRINCIPLE 02]

[PART 02 :: TRUST BOUNDARIES, CREDENTIALS & PERMISSIONS]

The Four Architectural Gates of Machine Identity

These four gates provide a review structure for workload identity. The cloud-specific dependency graph determines deployment order; existing resources, federation providers and permission bindings have different prerequisites.

[GATE 01 :: BOUNDARY]

Where It Lives

Review: Confirm the intended account, tenant, subscription or project, deployment context and target resource.

Control: Reference existing assets where appropriate, inspect planned changes and protect deployment state. Deletion safeguards reduce risk within their documented limits.

[GATE 02 :: PRINCIPAL]

Who the Machine Is

Review: Identify the workload principal, its owners and any alternate credential paths.

Control: Use managed identity or federation where suitable. Avoid introducing persistent workload secrets and remove unnecessary interactive application settings where applicable.

[GATE 03 :: FEDERATION]

How It Authenticates

Review: Check the issuer, audience, subject or attribute conditions and the source workload protections.

Control: Match current platform claims and restrict trusted sources. Test unauthorized branches or workloads as well as the allowed path; handle propagation with bounded retries.

[GATE 04 :: AUTHORIZATION]

What It Can Touch

Review: Specify required operations and evaluate effective permissions, including inherited and resource-based grants.

Control: Scope access to necessary resources and actions. Test expected denials and avoid broad administrative roles as a shortcut for workload access.

[PART 03 :: HUMAN-GOVERNED AI ASSISTANCE]

Use AI to Accelerate Engineering, with Clear Execution Authority

The System Directive structures the conversation around discovery, configuration, troubleshooting and review. In the advisory setup, the engineer executes commands and retains cloud credentials. Instructions in a prompt can guide model behavior, but reliable execution gates require controls outside the model.

1. Discover Before Generating

Ground configuration in observed cloud objects and current provider schemas. Ask for missing inputs, identify assumptions and stop when the deployment boundary is uncertain.

2. Review Before Applying

Inspect generated code and planned changes before execution. Separate workload permissions from the privileged permissions needed to provision the identity.

3. Validate Before Claiming

Use targeted request results and audit events to support each conclusion. A pipeline green check or an API-volume spike alone does not establish least privilege or complete security.

4. Diagnose Before Expanding

Bound repeated troubleshooting attempts, retain the defect history and restore a known baseline when needed. Treat new capabilities as reviewed changes with their own tests.

[PART 04 :: SEVEN-PHASE WORKFLOW]

From Discovery to Deployment Evidence & Handoff

The sequence below describes the workflow and its review criteria. Assess each demonstration against its published configuration, actual test results and stated scope. A completed phase does not imply that every criterion has passed.

Phase 01

Scope & Workspace Preparation

Establish the workload, target resource, cloud boundary, infrastructure state and tooling. Choose an approved execution environment and identify the owner of the change.

Discover the baseline: Use read-only queries to confirm the current context, existing resources and identity configuration.
Prepare state & files: Keep configuration, deployment state and credentials under appropriate access controls. A clean folder helps organization; it is not a security boundary.
Phase 02

Federation Metadata & Trust Design

Resolve issuer and workload claims from the selected platform. Review repository, environment, branch or Kubernetes service account conditions before writing the trust policy.

Use current claim formats: Check canonical names, required identifiers and any custom subject configuration. Do not infer token claims from naming conventions alone.
Define allowed & denied sources: Document which workloads may authenticate and which cases must fail, including relevant fork, branch and environment scenarios.
Phase 03

Infrastructure Payload & Change Review

Generate the configuration and an explicit execution runbook for the selected cloud and tool. The Architect reviews the plan, scope and recovery path before applying changes.

Protect existing infrastructure: Use references or deliberate imports as appropriate. Review replacements, deletions and identity changes rather than assuming a lifecycle flag prevents every destructive action.
Apply scoped trust & access: Configure the principal, federation and necessary permissions. Validate the actual administrative authentication requirements instead of assuming a particular login flow always supplies MFA.
Phase 04

Architecture Record & Live Validation

Record the deployed configuration in the Identity Architecture Ledger (IAL), then run a validation workload against the intended resource without logging secret values.

Record the baseline honestly: Capture identifiers, trust conditions, resource scope and configured session limits. Mark behavioral checks pending until their tests run.
Exercise the access boundary: Verify the allowed operation and expected denials. Distinguish an authorization rejection from network, syntax, service or credential errors. Metrics provide supporting context.
Phase 05

Audit Evidence & Defect Records

Use the Audit Results Ledger (ARL) to connect each conclusion to a specific test or log record. Keep the Defect & Patch Ledger (DPL) alongside the configuration.

Separate results from queries: A generated CloudTrail, KQL or Cloud Audit query is a handoff artifact. The related verification remains pending until the query runs against the correct schema and its results are reviewed.
Retain evidence & limitations: Preserve timestamps, principal and resource identifiers, request outcomes and relevant run references. Record failures, missing logs and untested conditions.
Phase 06

Repository Review & Handoff

Review configuration and documentation before synchronizing the authorized repository and branch. Keep sensitive deployment state and credentials out of the publication.

Inspect the staged changes: Use explicit file selection and secret checks. Ignore rules do not remove files already tracked in Git or secrets from prior commits.
Retain reproducibility: Commit appropriate dependency lock files and the reviewed configuration. Resolve branch differences deliberately and record the deployed revision.
Phase 07

Review, Lessons & Next Version

Close the session with an evidence-based review of completed work, unresolved defects and accepted limitations. The Architect decides which tested lessons should change the directive.

Bound troubleshooting: The original design uses three patch attempts before a fourth-attempt halt. This is a chosen review threshold; it is not a scientifically established reliability boundary.
Review proposed upgrades: Compare the proposed directive changes with the observed defect, check for contradictions and test their behavior before adopting a new baseline.
What the Ledgers Establish
The IAL, ARL and DPL organize the configuration, observed results and change history. Markdown files are editable records. Cryptographic integrity or independent attestation requires additional mechanisms and verification; generating a ledger does not provide certification or guarantee audit acceptance.

The Execution Triad: Human Authority, Workflow & AI Assistance

Three named roles make responsibilities explicit. The directive and AI remain part of the same conversational system; the human execution boundary is established by how credentials and tools are actually configured.

[HUMAN AUTHORITY]

1. The Architect

Owns the deployment scope, credential access and acceptance decision.

  • Reviews & executes: Checks the proposed change, runs approved commands and provides relevant outputs with secrets removed.
  • Accepts the result: Reviews allowed and denied test cases, unresolved risks and the recovery plan.
  • Controls publication: Approves which configuration and evidence can be shared or committed.
[WORKFLOW DEFINITION]

2. The System Directive

Defines the phase sequence, terminology, requested evidence and troubleshooting boundaries.

  • Organizes the work: Requests discovery before synthesis, human review before execution and evidence before success claims.
  • Provides a review checklist: Makes omissions and deviations easier to identify across the four gates and five guardrails.
  • Has a defined limit: A prompt in the same chat is not an independent supervisor. Tool permissions and external approval systems must enforce any automated execution boundary.
[ENGINEERING ASSISTANCE]

3. The AI Engine

Drafts code, explains tradeoffs and helps diagnose errors within the agreed scope.

  • Produces reviewable artifacts: Generates configuration, runbooks, validation scripts and record templates for the chosen environment.
  • Reports uncertainty: Separates hypotheses from observed causes and identifies when more evidence is needed.
  • Supports the engineer: In the advisory configuration, it has no deployment credentials. Adding tools or cloud access changes the risk model and requires separate controls.

Under the Hood: Four Operational Checks

  • Workspace & state: Use an approved, reproducible environment, with access-controlled state, backups and recovery procedures. Local terminals and cloud shells have different persistence settings; evaluate the actual configuration.
  • Federation & readiness: Inspect actual claims and trust conditions. A fixed delay may help with eventual consistency, but cannot prove readiness. Diagnose propagation errors and use bounded retries without weakening the policy to make a test pass.
  • Validation & audit: Collect request-level results that identify the principal, resource, operation and outcome. Audit ingestion delays vary; record pending work and return to it before closing the related evidence gate.
  • Day-2 changes: Recheck ownership, effective permissions, alternate credentials and the current baseline. Apply new controls through a reviewed plan and test both intended access and unintended access paths.
Enterprise Deployment Considerations
The workflow can be adapted to an organization-approved AI environment. Data handling depends on the selected service, region, retention settings, network controls, integrations and organizational policy. A private endpoint or parameterized prompt alone does not establish complete data loss prevention.

Four Governance Practices & Five Configuration Guardrails

The approach draws on established security and AI risk-management ideas. Referencing a framework does not establish certification, standards compliance or independently validated model reliability.

[GOVERNANCE PRACTICES]
  • Grounding in external evidence: Use authoritative APIs and observed results to challenge model assumptions. The ReAct research pattern is a useful influence, with benefits that depend on the task and implementation.
  • Bounded authority: Limit credentials and tools to the task. The advisory workflow keeps execution with the engineer; an integrated agent needs external permission and approval controls.
  • Accountability & review: Assign ownership, define acceptance criteria and document risk decisions. NIST AI RMF provides voluntary guidance for managing AI risk.
  • Bounded troubleshooting: Stop repeated unsuccessful changes, retain the error history and reconsider the assumptions. Use a chosen retry budget and evidence-based options rather than an unsupported numerical probability of success.
[FIVE CONFIGURATION GUARDRAILS]

These are review targets for the generated configuration and its operation. Their status must reflect the deployed controls and collected evidence, including failures or pending checks.

1. Credential & Context Protection

  • Control: Avoid sharing credentials with the model. Prefer federation or managed identity where suitable, minimize sensitive output and handle setup tokens through an approved secret-input mechanism.
  • Verify: Review prompt inputs, command history, logs and artifacts. Account and tenant IDs are routing identifiers, not authentication secrets, although organizational policy may restrict their disclosure.

2. Existing Asset & State Protection

  • Control: Reference existing resources deliberately, inspect proposed changes and protect state with access controls, locking, recovery and appropriate deletion safeguards.
  • Verify: Check the plan for replacement or deletion. Read-only references and lifecycle protections have specific limits and do not prevent all changes through other paths.

3. Least-Privilege Workload Access

  • Control: Grant only necessary operations on the required resources. Keep provisioning authority separate from workload access and review all applicable grants.
  • Verify: Test an allowed operation and meaningful denied operations. Examine inherited roles, resource policies, impersonation and alternate credential paths. A narrow new policy alone does not establish narrow effective access.

4. Dependency & Schema Review

  • Control: Use reviewed dependencies, appropriate lock files and current schemas for the selected tool. Prefer immutable action references when the platform supports them.
  • Verify: Inspect actual resolved versions and hashes. Version selection improves reproducibility but does not establish that a dependency is safe or that the generated configuration is correct.

5. Secret-Safe Validation Output

  • Control: Avoid printing tokens or retrieved secret values. Use platform-supported masking as a secondary safeguard; keep shell tracing and verbose credential output under control.
  • Verify: Inspect logs and artifacts for exposure. GitHub Actions masking redacts matching log output; it does not erase process memory or automatically protect every transformed value or other execution platform.

Provider-Specific Federation

Choose the supported identity mechanism for the workload. Discover actual issuer and claim settings, review the trust expression and test both accepted and rejected sources. Numeric repository IDs, Kubernetes identities and CI service connections are not interchangeable.

Existing & New Infrastructure

For brownfield work, inspect and preserve the current baseline while planning intended changes. For greenfield work, include state protection, ownership and recovery from the beginning. Review each change rather than assuming additive code is automatically safe.

Resource-Specific Authorization

Match the required operation to the provider’s actual authorization model. Secret retrieval, key signing, object reads and database queries require different permissions and tests. Check credential expiry for the deployed mechanism instead of assuming a universal one-hour maximum.

Day-2 Review & Expansion

Extend the baseline only after checking prerequisites, applicability and impact. Conditional Access, AWS organization policies and Google Cloud service perimeters address different risks. Retest trust and access after changes, and retain the recovery procedure.

Current Scope & Direction

Future work includes broader negative testing, externally enforced review gates and repeatable checks across cloud implementations.
