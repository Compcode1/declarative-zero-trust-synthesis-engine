Architectural Perspectives

In cloud identity security, relying on an untethered generative AI model to write deployment scripts all at once is a major operational risk. Left on its own, a probabilistic AI engine will guess resource IDs, invent broken syntax, or grant overly broad permissions just to clear an error. To solve this for my Microsoft Entra ID and Azure deployments, I applied formal AI systems engineering best practices to build the Zero Trust Interactive State Machine. This framework tethers that probabilistic AI engine to a master System Directive to make its output deterministic. [LAYER 1: AI SYSTEMS ENGINEERING PILLARS]
The 4 Core AI Engineering Pillars of My System Directive

Out of the box, generative AI is a probabilistic engine. When asked to write a cloud security script without strict boundaries, it will guess missing resource IDs, invent outdated syntax, or grant overly broad administrative permissions just to clear an error. To tether that probabilistic engine and make its output deterministic, I built my master System Directive around four globally recognized AI Systems Engineering standards, separating what each standard defines in the AI industry from how I wired it into my workflow at the keyboard:

1. Agentic Patterns (The ReAct Framework)
The AI Systems Engineering Standard (Yao et al.) Developed by researchers at Princeton and Google Brain, the ReAct (Reasoning and Acting) methodology prevents language models from guessing in a vacuum by forcing them to alternate between reasoning steps and checking real external data sources.
How I Applied It in My System Directive In Phases 1 and 2, the AI is forbidden from guessing Azure or pipeline identifiers. Instead, it pauses, gives me native read-only terminal lookup commands, waits for me to paste back the real console output, and only generates deployment code in Phase 3 using verified live IDs.
2. Bounded Autonomy (OWASP Top 10 for LLMs: LLM08)
The AI Systems Engineering Standard (OWASP LLM08: Excessive Agency) The global OWASP application security standard for artificial intelligence, which mandates strict permission boundaries so an AI model cannot exercise unchecked agency or run destructive commands across enterprise systems.
How I Applied It in My System Directive The AI Engine has zero direct access to my cloud account and is locked inside hard rules that force read-only lookups for existing Brownfield resources, single-vault data permissions (blocking Owner and Contributor), and a guided Azure Portal handoff whenever a role assignment requires interactive multi-factor authentication.
3. Human-in-the-Loop Governance (NIST AI RMF 1.0)
The AI Systems Engineering Standard (NIST AI Risk Management) The U.S. federal standard establishing the "Govern" function, requiring continuous human oversight, risk control, and clear human accountability at every critical decision point in a high-impact AI system.
How I Applied It in My System Directive My System Directive forbids the AI from skipping ahead or stacking manual steps. It must halt at every single phase, from locking in coordinates and extracting OIDC strings to running the live validation pipeline and checking Azure Portal metrics, waiting for my explicit verification and sign-off before advancing.
4. Cognitive Circuit Breaking (Hallucination Prevention)
The AI Systems Engineering Standard (Huang et al.) Grounded in foundational AI reliability research, cognitive circuit breaking stops language models from drifting off their instructions and repeating false guesses ("hallucination spirals") during multi-turn troubleshooting sessions.
How I Applied It in My System Directive Active across every phase of the build: if a terminal command or script fails 3 times in a row at any point, Iteration 4 trips a hard Circuit Breaker that forbids the AI from writing new code. Instead, it forces the AI to audit its own three prior attempts and calculate an Estimated Probability of Success percentage so I can decide whether to continue or pivot.

[LAYER 2: TRANSLATING AI STANDARDS INTO CODE]
The 5 Enterprise Guardrails (Built-In Safety Locks)

While the four AI Systems Engineering pillars above govern how the AI behaves across the conversation, I translated those principles, alongside specific controls from the OWASP Top 10 for LLMs and the NIST AI Risk Management Framework, into five concrete Enterprise Guardrails inside the generated code itself. Formally verified and scored as [PASS] in my Phase 5 Audit Results Ledger, these five safety locks prevent the five most common failures in automated cloud deployments:

1. Secret & Credential Protection OWASP LLM06 & NIST Privacy: Separates non-secret routing addresses from private secrets. My Tenant ID, Subscription ID, Resource Group, and repo name are resolved via terminal lookups so the AI writes 100% finished code with zero placeholders, while 60-minute OIDC eliminates passwords and invisible terminal typing keeps personal tokens off the screen.
2. Existing Asset Protection OWASP LLM08 (Idempotency): Prevents scripts from overwriting or deleting live cloud resources. Forces read-only lookup mode when I connect to existing Brownfield vaults or databases, and attaches deletion-prevention locks and permanent state storage rules when I build brand-new Greenfield infrastructure.
3. Stopping "The Contributor Trap" OWASP LLM08 (Least Privilege): Stops the AI shortcut of granting broad administrative roles like Owner or Contributor that could delete resources across Azure. Locks permissions strictly to the specific data action required on one single Key Vault, Storage Account, or database ID.
4. Pinned Provider Versions OWASP LLM05 (Supply Chain Safety): Rejects floating version tags (like "latest") and pins every Terraform provider, Azure Bicep resource API, and CI/CD pipeline action to an exact, verified version number. Also enforces pure Microsoft Graph JSON formatting on PowerShell REST API builds.
5. Pipeline Log Token Masking OWASP LLM02 & LLM06 (Output Scrubbing): Injects active runtime log masking into my Phase 4 validation workflow so the pipeline runner scrubs any temporary 60-minute OIDC token or vault secret with asterisks (***) in memory before a single line can print to the console screen.

[LAYER 6: TROUBLESHOOTING, DPL, CIRCUIT BREAKER & PHASE 7 COMPILATION]
Troubleshooting, The Defect & Patch Ledger, The Circuit Breaker & Phase 7 Upgrades

Even with careful planning, real-world cloud deployments can hit unexpected friction such as a Microsoft API schema quirk, a propagation delay, or a terminal permission block. My System Directive handles errors across every phase using two distinct mechanisms: first, a standard patch loop that logs every verified fix in the Defect & Patch Ledger (DPL); and second, an emergency 4-Iteration Circuit Breaker that only trips if an error is still unresolved on Iteration 4:

1. Standard Patch Loop & State Re-Sync (Iterations 1 to 3) Whenever a terminal command or script returns an error during any phase, the AI immediately drops all analogies and enters clinical diagnostic mode for up to 3 focused attempts. Once I confirm a fix works in my terminal, the System Directive forces a full-file State Re-Sync, outputting the complete infrastructure file from top to bottom so partial code snippets never corrupt my workspace.
2. Real-Time Defect & Patch Ledger (patch_ledger.md) Logging an entry in the Defect & Patch Ledger does not require hitting the Circuit Breaker. Every time I verify a working fix during Iterations 1, 2, or 3, the root cause and exact engineering solution are staged immediately as a real-time DPL entry and saved into patch_ledger.md in Phase 5.
3. The 4-Iteration Circuit Breaker (Iteration 4 Halt) If a specific error fails 3 times in a row and reaches Iteration 4, the Circuit Breaker trips automatically. The State Machine forbids the AI from generating any new code and forces a Risk Management Assessment: the AI must analyze the error shifts across its 3 failed tries, output an Estimated Probability of Success (X%), and present alternative pathways for my decision.
4. Phase 7 Scorecard & System Directive Compilation At session close in Phase 7, the machine outputs my statistical AI Performance Scorecard (counting every diagnostic loop, iteration, circuit breaker, and protocol deviation). It then extracts every proven fix from the Defect & Patch Ledger and compiles the newly upgraded System Directive into a single code block.
[INDUSTRY AI SYSTEMS ENGINEERING CLASSIFICATION]
L4 Agentic Architecture Under Strict Human-in-the-Loop (HITL) Governance

Where does my Zero Trust Interactive State Machine sit within standard AI industry classifications? Rather than letting an AI model operate as an unchecked autonomous agent, or relying on one-shot unverified prompting, I engineered an L4 Agentic Architecture governed by strict human-in-the-loop authority. By tethering a probabilistic AI engine to my master System Directive, I harness the speed of automated multi-language code synthesis while keeping every state transition, terminal command, and cloud deployment under my direct control:

1. Applied Control Theory (Brakes & Steering)

Full Human Authority Across All 7 Phases: In systems engineering, control theory means putting reliable steering and emergency brakes on a powerful engine. By requiring my explicit verification at every phase of the build, and enforcing a 4-Iteration Circuit Breaker that halts code generation and calculates an Estimated Probability of Success percentage if any error fails 3 times, my System Directive gives me complete steering and braking authority over the AI Engine.

2. High-Assurance Verification (Two-Stage Live Proof)

Baseline Ledger, Portal Metrics & Audit Proof: In enterprise cloud security, a script finishing without an error message is never enough. I must mathematically prove the deployed configuration works. In Phase 4, I generate identity_architecture_ledger.md (IAL), run the live validation pipeline, and check Azure Portal Monitoring Metrics (Total Service API Hits over 30 minutes) for immediate proof of data-plane access, followed in Phase 5 by audit_results_ledger.md (ARL) and asynchronous KQL log queries (kql_telemetry.md) proving zero HTTP 403 Forbidden drops.

3. Continuous Rulebook Evolution (Self-Improving Harness)

Real-Time DPL Staging & Phase 7 Compilation: Instead of solving a cloud timing bug or API error once and losing the lesson when the chat window closes, every fix I verify in my local terminal is staged in real time inside patch_ledger.md (the Defect & Patch Ledger). In Phase 7, I review the AI Performance Scorecard and compile those proven fixes permanently into my master System Directive, turning 28+ iterations of real-world cloud troubleshooting into a hardened, self-improving rulebook.
