[APPLICATION CONTEXT :: TRAINING, SIMULATION & SOFTWARE DELIVERY]

Why Cloud Workload Identity Matters to Autonomous Systems

Robotics, connected-vehicle and space-system teams may use cloud services to train models, run simulation, store operational data and deliver software. Automated jobs need access to those services, often through machine identities such as IAM roles, service principals or service accounts.

A compromised workload or misconfigured trust policy can expose valuable data or release infrastructure. The engineering task is to define which workload may authenticate, which operations it needs and how those boundaries will be tested.

AKCCE applies the four-gate review structure to these cloud connections. The engineer retains execution authority in the advisory workflow; the cloud provider’s deployed policies enforce access.

How to Read This Page

The seven areas below map practical risks to workflow controls and evidence to collect. They are an AKCCE review structure, not a claim that all intrusions follow seven stages. The sources describe relevant risks and practices; they do not certify or endorse AKCCE.
REVIEW AREA 01 PHASE 1 / GATE 1

Workstation Credentials & Deployment Boundaries

[RISK SCENARIO]

How the Exposure Can Arise

An attacker with access to an engineering workstation or runner may recover credentials from command history, files or cached sessions. Separately, an engineer can accidentally run a valid deployment against the wrong account or production resource.

[ASSETS & TRUST BOUNDARIES]

What to Examine

  • Setup credentials: Tokens or keys embedded in command arguments, scripts or shared troubleshooting output.
  • Execution context: The active account, tenant, subscription, project and resource selection.
  • Workspaces & state: Local files or persistent cloud-shell storage that require access control and appropriate cleanup.
[SUPPORTING REFERENCES]

Relevant Security Guidance

  • MITRE ATT&CK: Shell History (T1552.003): Describes credential recovery from shell history on compromised systems.
    Read the source →
  • OWASP NHI2:2025 — Secret Leakage: Covers exposed keys, tokens and other non-human identity credentials.
    Read the source →
[WORKFLOW RESPONSE]

Controls & Acceptance Checks

  • Discover before changing: Confirm the current identity, cloud context and intended target through read-only queries.
  • Handle credentials deliberately: Keep credentials out of chat and source code. Use an approved secret-input method instead of putting sensitive values directly in command arguments.
  • Use an approved environment: Assess host security, session persistence and state protection. A clean folder or a local terminal alone does not provide isolation.

Evidence to collect: Record the discovered deployment context and review the runbook, logs and staged files for credential exposure. Account and tenant IDs identify routes; they are not authentication secrets.

REVIEW AREA 02 PHASE 2 / GATE 3

Overly Broad Federation Trust

[RISK SCENARIO]

How the Exposure Can Arise

A signed workload token can be accepted from an unintended source when a trust policy is too broad. This is a trust-configuration problem: the attacker may be using a legitimately issued token rather than forging its signature. Repository, branch, environment and service-account conditions must match the intended workload.

[ASSETS & TRUST BOUNDARIES]

What to Examine

  • Release jobs: Trust that admits an unapproved repository, branch or execution context.
  • Training & simulation workloads: Namespaces, service accounts or runners with access beyond their intended purpose.
  • Trust conditions: Issuer, audience, subject and provider-specific attribute rules.
[SUPPORTING REFERENCES]

Relevant Security Guidance

  • OWASP NHI6:2025 — Insecure Cloud Deployment Configurations: Includes insufficient validation of OIDC tokens and their claims.
    Read the source →
  • GitHub OIDC reference: Documents claims, subject formats and trust-condition inputs for GitHub Actions.
    Read the source →
[WORKFLOW RESPONSE]

Controls & Acceptance Checks

  • Inspect actual claims: Resolve the issuer and configured claim format from the workload platform. Use immutable identifiers where supported and relevant.
  • Constrain the trusted source: Use exact matching or appropriately bounded provider-specific conditions. Avoid expanding trust just to bypass a deployment error.
  • Protect the trusted job: Review workflow permissions, repository protections and runner security. An attacker inside an authorized job may still obtain its intended credentials.

Evidence to collect: Test the intended workload and selected unauthorized claim or source cases. Record the credential lifetime for the actual mechanism; a universal one-hour limit cannot be assumed.

REVIEW AREA 03 PHASE 3 / GATES 2 & 4

Excessive Permissions & Access to Adjacent Resources

[RISK SCENARIO]

How the Exposure Can Arise

A compromised build or simulation job can misuse every operation its identity is allowed to perform. Broad administrative access can permit resource changes or privilege escalation. Cloud role semantics differ: infrastructure-management permission does not always include direct data reads, but may create other routes to sensitive access.

[ASSETS & TRUST BOUNDARIES]

What to Examine

  • Model weights & datasets: Reads or changes outside the workload’s required model and data scope.
  • Customer & operational information: Facility maps, sensor records and telemetry that require appropriate confidentiality and retention controls.
  • Release infrastructure: The ability to change trust policies, permissions, storage or signing-service configuration.
[SUPPORTING REFERENCES]

Relevant Security Guidance

  • OWASP NHI5:2025 — Overprivileged NHI: Addresses machine identities granted more privilege than their function needs.
    Read the source →
  • AWS IAM policy evaluation: Explains how applicable policy types contribute to the access decision.
    Read the source →
[WORKFLOW RESPONSE]

Controls & Acceptance Checks

  • Define required operations: Select actions and resource scope from the workload’s actual task. Separate provisioning authority from runtime access.
  • Review effective access: Consider inherited grants, resource policies, impersonation and alternate credentials. A narrow new policy does not cancel existing permissions.
  • Review infrastructure changes: Inspect planned replacements, deletions and permission changes; use appropriate state and deletion safeguards.

Evidence to collect: Test required reads or operations and relevant denied operations on adjacent resources. Record policy evidence and any remaining access paths rather than declaring zero lateral movement.

REVIEW AREA 04 PHASE 4 / VALIDATION

Secret-Safe Validation & Signing Authority

[RISK SCENARIO]

How the Exposure Can Arise

Debug output can expose active tokens or retrieved secrets in shared logs and artifacts. Firmware signing introduces a separate boundary: permission to read a secret, invoke a signing operation, approve a release and install an update are different capabilities.

[ASSETS & TRUST BOUNDARIES]

What to Examine

  • Runtime credentials: Bearer tokens and API credentials exposed through tracing or output.
  • Signing authority: Private-key custody and the permissions that permit artifacts to be signed.
  • Release integrity: Which artifact is approved, signed and accepted by the target device.
[SUPPORTING REFERENCES]

Relevant Security Guidance

  • GitHub Actions masking: Describes masking values in logs; this is log redaction, not memory erasure.
    Read the source →
  • NHTSA 2022 guidance & AWS KMS: NHTSA addresses firmware and OTA integrity. AWS KMS documentation distinguishes managed asymmetric key operations from exporting a private key.
    Read the source →
[WORKFLOW RESPONSE]

Controls & Acceptance Checks

  • Avoid printing secret values: Validate outcomes using non-sensitive assertions. Treat platform masking as a secondary safeguard and inspect artifacts as well as logs.
  • Design signing separately: For real release signing, assess managed signing or protected key custody, narrowly scoped signing permission and independent release authorization.
  • Record the deployment baseline: Use the Identity Architecture Ledger to document configuration. Behavioral checks remain pending until their tests run.

Evidence to collect: Retain the principal, resource, operation and result without publishing credentials. A secret-read test establishes neither a successful firmware signature nor device-side verification or rollback protection.

REVIEW AREA 05 PHASE 5 / EVIDENCE REVIEW

Audit Coverage, Ingestion Delays & Evidence Quality

[RISK SCENARIO]

How the Exposure Can Arise

Incomplete audit coverage and delayed ingestion can leave a deployment insufficiently understood. The timing depends on the service, logging configuration and monitoring pipeline. A generated query or an aggregate activity spike cannot establish which identity performed a successful data operation.

[ASSETS & TRUST BOUNDARIES]

What to Examine

  • Visibility: The relevant authentication, data access and configuration-change events.
  • Attribution: Enough principal, resource, operation and timing information to investigate a request.
  • Handoff accuracy: Audit records that distinguish observed results from assumptions and pending work.
[SUPPORTING REFERENCES]

Relevant Security Guidance

  • OWASP CI/CD: Insufficient Logging and Visibility (CICD-SEC-10): Identifies inadequate pipeline visibility as a security risk.
    Read the source →
  • NSA/CISA CI/CD guidance: Provides broader recommendations for securing the development and delivery environment.
    Read the source →
[WORKFLOW RESPONSE]

Controls & Acceptance Checks

  • Define evidence prerequisites: Check that the required events are enabled, retained and available to the reviewer. Keep monitoring health visible.
  • Correlate supported fields: Use the provider’s actual log schema and documented identifiers. Record ambiguity where a unique linkage cannot be established.
  • Report the actual result: Populate the Audit Results Ledger with evidence-backed PASS, FAIL, PENDING or ERROR statuses as appropriate.

Evidence to collect: Run the queries and review their results before closing the related check. Record missing events and uncertain attribution. Detection, response and access controls remain complementary responsibilities.

REVIEW AREA 06 PHASE 6 / HANDOFF

Deployment State & Repository Exposure

[RISK SCENARIO]

How the Exposure Can Arise

State, plan files and environment files may contain sensitive configuration or credentials. Repository readers can recover exposed information from commits. Unreviewed synchronization or history changes can also remove validated configuration or obscure what was deployed.

[ASSETS & TRUST BOUNDARIES]

What to Examine

  • Infrastructure state & plans: Provider-managed metadata and sensitive values retained in deployment artifacts.
  • Repository history: Credentials or state files already committed, even if later ignored.
  • Reproducibility: The configuration, dependency locks and workflow revision used for a deployment.
[SUPPORTING REFERENCES]

Relevant Security Guidance

  • HashiCorp: Manage sensitive data: Explains sensitive information in state and plan files and the need to protect it.
    Read the source →
  • MITRE ATT&CK: Code Repositories (T1213.003): Describes collection of valuable data from compromised repositories.
    Read the source →
[WORKFLOW RESPONSE]

Controls & Acceptance Checks

  • Protect state deliberately: Use an approved backend or storage with access control, encryption, locking and recovery suitable for the tool and environment.
  • Review before staging: Use explicit file selection, appropriate ignore rules and secret checks. Preserve the dependency locks needed for reproducibility.
  • Synchronize deliberately: Inspect the working tree, branch and remote changes. Resolve differences through review rather than assuming a pull command prevents conflicts.

Evidence to collect: Inspect the staged diff and tracked files. Ignore rules do not remove already tracked files or historical exposure. Revoke exposed credentials and follow the incident process where needed.

REVIEW AREA 07 ALL PHASES / PHASE 7

Configuration Drift & AI-Assisted Change Review

[RISK SCENARIO]

How the Exposure Can Arise

As environments and workloads grow, configuration can diverge and earlier decisions can be lost. AI-generated patches may introduce incorrect assumptions or weaken a policy while resolving an error. A chat history is an unreliable substitute for a reviewed, versioned baseline.

[ASSETS & TRUST BOUNDARIES]

What to Examine

  • Trust & permission baselines: New environments that silently acquire broader access or outdated assumptions.
  • Troubleshooting history: Errors, tested fixes and exceptions needed to understand later changes.
  • Execution authority: The credentials and tools made available to an assistant or integrated agent.
[SUPPORTING REFERENCES]

Relevant Security Guidance

  • NIST AI Risk Management Framework: Provides voluntary guidance for managing AI risk and accountability.
    Read the source →
  • OWASP LLM06:2025 — Excessive Agency: Addresses excessive functionality, permissions and autonomy in AI systems.
    Read the source →
[WORKFLOW RESPONSE]

Controls & Acceptance Checks

  • Retain the baseline: Version the configuration and defect record, including evidence and unresolved issues. Recheck current cloud state before Day-2 changes.
  • Bound repeated patches: Use a defined retry budget and an engineer-led review when troubleshooting stalls. The original fourth-attempt halt is a design choice, not a proven reliability threshold.
  • Review proposed lessons: Test directive changes before adoption and check for conflicting rules. External tool permissions and approval gates must enforce automated execution limits.

Evidence to collect: Use repeatable checks to detect drift and regressions. A complete file or a larger prompt does not guarantee correctness; record what was tested and what remains open.

[FIVE ARTIFACT GROUPS :: CONFIGURATION, EVIDENCE & CHANGE HISTORY]

A Reviewable Engineering Handoff

The intended handoff brings the implementation and its evidence together. These are five artifact groups, not a guarantee of exactly five files. Review sensitive content before publishing or committing the package.

[CONFIGURATION & RUNBOOK]

1. Infrastructure Payload & Execution Runbook

The cloud-specific configuration, prerequisites and commands for the reviewed change. Retain appropriate version locks, plan review, workload trust and permission scope. A deployment may require several files, modules and workflow definitions.

[ARCHITECTURE BASELINE]

2. Identity Architecture Ledger

identity_architecture_ledger.md records the deployed principal, trust conditions, resource scope, credential settings and configuration revision. It describes the baseline and links to supporting observations.

[OBSERVED RESULTS]

3. Audit Results Ledger

audit_results_ledger.md records each check, its evidence, outcome and limitations. Separate completed tests from pending verification. The ledger can support a review, but does not establish regulatory compliance or guarantee audit acceptance.

[LOGGING & QUERY HANDOFF]

4. Telemetry Queries & Results

Provider-specific CloudTrail, KQL or Cloud Audit queries, with prerequisites, schema assumptions and reviewed results when available. A query file is not an active detector or an executed verification result.

[DEFECTS & CHANGES]

5. Defect & Patch Ledger

patch_ledger.md records error signatures, root-cause confidence, tested fixes, exceptions and unresolved issues. Proposed workflow improvements remain subject to review and regression checks.

[ENGINEERING SUMMARY]

Seven Review Areas, Controls & Evidence

Acceptance depends on the selected implementation and recorded results.
Review Area Example Risk Workflow Response Evidence
1. Credentials & context Exposed setup credentials or commands directed at the wrong environment. Approved workspace, controlled credential handling and read-only context discovery. Recorded context, reviewed commands and inspected artifacts.
2. Federation trust Tokens from an unintended source satisfy an overly broad trust condition. Current claim discovery, narrow trust and protection of the trusted job. Allowed authentication plus meaningful rejected-source tests.
3. Effective permissions A compromised job can read, change or administer more than its task requires. Operation-level scope, effective-permission review and change-plan inspection. Policy review, allowed operations and expected denials.
4. Secrets & signing Credentials leak in output, or secret retrieval is mistaken for validated release signing. Minimal output, supported redaction and separate signing/release controls. Inspected logs; distinct access, signing and device tests when applicable.
5. Audit evidence Missing or delayed events lead to unsupported success and compliance claims. Explicit logging prerequisites and evidence-linked result statuses. Executed queries, reviewed events and documented coverage limits.
6. State & repositories Sensitive deployment artifacts enter the repository or reviewed configuration is overwritten. Protected state, explicit staging and deliberate branch synchronization. Reviewed staged diff, tracked-file checks and deployed revision.
7. Drift & AI review Repeated configuration mistakes or AI-generated changes weaken the baseline. Versioned records, bounded troubleshooting and reviewed updates. Change diffs, regression results and current-state checks.
