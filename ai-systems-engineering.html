[SECTION 01 :: HOW MY SYSTEM DIRECTIVE IS STRUCTURED]

Anatomy of the Zero Trust Interactive State Machine

Instead of relying on an open-ended prompt, my Zero Trust Interactive State Machine (v9.2) is governed by a structured master System Directive divided into three architectural layers:
  • Layer 1 (The Tethered Compute Engine): Subordinates The AI Engine to my human sign-off so it can only output terminal lookup queries in Phases 1 and 2 and synthesize my IaC Payload in Phase 3 after my coordinates are locked.
  • Layer 2 (The 7-Phase State Machine Harness): Enforces mandatory phase halts, a continuous Watchdog turn check, and strict separation between hard execution constraints and passive UI presentation strings.
  • Layer 3 (Two-Stage Verification & Continuous Improvement): Enforces the Phase 4 Identity Architecture Ledger (IAL), Validation Bridge, and Azure Portal Monitoring Metrics (Total Service API Hits), followed by the Phase 5 Audit Results Ledger (ARL), KQL Telemetry, and Defect & Patch Ledger (DPL), and Phase 7 System Directive Compilation.
[LAYER 01 : THE AI ENGINE]

The Tethered Co-Pilot

  • Zero Direct Cloud Access: The AI Engine has zero direct network access to my Entra ID Tenant ID or Azure Subscription ID and cannot execute commands on its own.
  • Lookups Before Synthesis: In Phases 1 and 2, it outputs read-only terminal lookup scripts so I can extract my real cloud and Execution Agent IDs. Only in Phase 3 does it synthesize the finished Terraform, Azure Bicep, or PowerShell REST API IaC Payload and Terminal Runbook.
[LAYER 02 : THE STATE MACHINE]

7 Phases & Strict Rules

  • Mandatory Halts & Watchdog Check: The State Machine paces my build across 7 sequential phases with strict human-in-the-loop halts and a continuous Watchdog self-check on every turn.
  • Presentation Subordination: Isolates passive telemetry table headers inside fenced XML blocks so cosmetic display text can never override a mechanical security rule across Gate 1 through Gate 4.
[LAYER 03 : BUILT-IN VERIFICATION]

Two-Stage Proof & Ledgers

  • Phase 4 Baseline & Metrics: Generates the Identity Architecture Ledger (IAL), runs the Validation Bridge on my Execution Agent, and verifies live access via Azure Portal Monitoring Metrics (Total Service API Hits) on my Data-Plane Asset.
  • Phase 5 & Phase 7 Evolution: Generates the Audit Results Ledger (ARL), KQL Telemetry (kql_telemetry.md), and Defect & Patch Ledger (DPL) in Phase 5, and compiles all upgrades into my System Directive in Phase 7.

The Four Pillars of My System Directive

To turn a probabilistic language model into a deterministic engineering co-pilot, I built my master System Directive (v9.2) on four globally recognized AI Systems Engineering standards:
  • Industry Standard vs. My Implementation: Each card below separates what the foundational AI Systems Engineering standard defines in the broader AI industry from how I wired it into my 7-phase workflow at the keyboard, followed by the primary research citation.
[PILLAR 01 :: TERMINAL VERIFICATION & REAL-TIME DPL LOGGING]

1. Agentic Patterns (The ReAct Framework)

  • The AI Systems Engineering Standard: Asking a model to write a complex cloud deployment in one shot ("zero-shot prompting") forces it to guess missing environment details. Developed by researchers at Princeton and Google Brain, the ReAct (Reasoning and Acting) methodology prevents hallucination by forcing models to alternate between reasoning steps and checking real external data sources.
How I Applied It in My System Directive (Phases 1 to 2 & All-Phase DPL)
  • Phase 1 & 2 Terminal Lookups: Before writing any code, The AI Engine pauses and gives me read-only terminal lookup commands so I can extract my real Entra ID Tenant ID, Azure Subscription ID, Resource Group, and exact Code Repository and Branch spelling from my Execution Agent.
  • Standard Patch Loop & State Re-Sync (Iterations 1 to 3): If an error occurs at any phase, The AI Engine enters clinical diagnostic mode for up to 3 attempts. Once I verify a fix in my local terminal, it logs the root cause and fix immediately in the Defect & Patch Ledger (DPL) and performs a full-file State Re-Sync of my entire IaC Payload.
Reference Standard
ReAct: Synergizing Reasoning and Acting in Language Models (Yao et al.)

Foundational research from Princeton and Google Brain demonstrating that language models stop hallucinating when forced to alternate between reasoning traces and external environment lookups.

[PILLAR 02 :: PERMISSION & MFA SAFETY LOCKS]

2. Bounded Autonomy (OWASP LLM08)

  • The AI Systems Engineering Standard: When an untethered model hits an access denial or multi-factor authentication error, it frequently attempts to bypass the error by granting broad administrative roles or overwriting live resources. OWASP LLM08 (Excessive Agency) mandates strict permission boundaries so a model cannot exercise unchecked agency.
How I Applied It in My System Directive (Phase 3 / Gates 1, 2 & 4)
  • Asset & Role Locks: The State Machine enforces read-only lookups on Brownfield (Existing) Data-Plane Assets, deletion-prevention locks on Greenfield (Net-New) Data-Plane Assets, Single-Tenant Application Registrations and Service Principals, and single-asset Data-Plane Roles (blocking Owner and Contributor Roles).
  • Azure Portal MFA Handoff: When a Conditional Access or PowerShell REST API build requires an interactive MFA popup to assign a Gate 4 Data-Plane Role (which local terminals drop), The State Machine separates the Data-Plane Role step from the IaC Payload and gives me a guided Azure Portal MFA Handoff checklist so the build never crashes.
Reference Standard
OWASP Top 10 for LLM Applications (LLM08: Excessive Agency)

The global application security standard for preventing artificial intelligence models from exercising unchecked permissions or executing destructive actions across enterprise infrastructure.

1. Preventing Microsoft Entra ID Sync Crashes

  • The Cloud Bug: When an IaC Payload creates a new Application Registration and Service Principal in Microsoft Entra ID (Gate 2) and immediately tries to attach an OpenID Connect (OIDC) Subject Claim or Conditional Access policy a split-second later (Gate 3), Microsoft's global directory servers often haven't finished syncing yet and the deployment crashes.
  • My Built-In Fix: My System Directive automatically injects a 30-Second Server Sync Timer into my Phase 3 IaC Payload between Gate 2 creation and Gate 3 attachment so Microsoft's directory servers catch up cleanly.

2. Preventing Subject Claim Casing Drops & IP Overflows

  • The Cloud Bug: Microsoft Entra ID rejects OpenID Connect (OIDC) token exchanges if a single capital or lowercase letter in the Subject Claim does not match my Code Repository and Branch spelling, and crashes if thousands of Execution Agent IPv4 ranges are fed into one Conditional Access policy block.
  • My Built-In Fix: Phase 2 extracts the exact capital-and-lowercase spelling of my Code Repository and Branch (such as CompCode1) via terminal lookup for the Subject Claim, and Phase 3 automatically chunks large IPv4 lists into safe blocks.

3. Beating Azure Portal Caching & Log Indexing Delays

  • The Cloud Bug: Azure Portal UI toggles suffer from browser caching delays, and Azure Log Analytics can take a long, unpredictable amount of time to index new sign-in logs.
  • My Built-In Fix: My System Directive mandates terminal audit scripts to verify policy states directly in Microsoft Entra ID before testing, and uses Two-Stage Live Verification: checking Azure Portal Monitoring Metrics (Total Service API Hits) on my Data-Plane Asset in Phase 4 for immediate proof before running asynchronous KQL Telemetry (kql_telemetry.md) in Phase 5.
