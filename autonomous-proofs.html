[EXAMPLE 01 :: GITHUB ACTIONS / AWS / SECRETS MANAGER]

A Recorded Federation & Secret-Access Exercise

This example connects a GitHub Actions job to an AWS IAM role through OpenID Connect, then reads a designated AWS Secrets Manager secret and attempts an account-level secret-listing operation. Terraform records the role, trust and permissions used in the exercise.

The secret contains simulated Ed25519 signing-key metadata. The exercise uses AWS services, but its published evidence covers workload authentication and selected resource operations. It does not demonstrate firmware signing, private-key custody, device acceptance or a production fleet rollout.

[SEVEN REVIEW AREAS :: OBSERVATIONS & LIMITS]

What the Published Example Supports

AREA 01 Source-inspected

Account Context

The AWS provider sets allowed_account_ids and includes a caller-identity lookup. These help establish the intended deployment account.

Review limit: The source snapshot does not establish host isolation, complete shell-history protection or the security of the bootstrap session.

AREA 02 Source-inspected

Federation & Session Duration

Trust uses StringEquals for the audience and a subject containing repository names plus numeric owner/repository IDs. The role maximum and workflow request are both 3600 seconds.

Review limit: These are numeric GitHub identifiers, distinct from opaque GraphQL node IDs. The complete configured subject must match. Authentication from unauthorized sources needs separate negative tests.

AREA 03 Source-inspected

Resource Permissions

The inline role policy grants GetSecretValue and DescribeSecret on one secret ARN. A resource-policy Allow names the role and account; block_public_policy is enabled.

Review limit: The resource Allow does not itself deny every other same-account identity. Effective access requires reviewing all applicable grants. An authorization denial for ListSecrets does not establish denial of every other secret read.

AREA 04 Run metadata + supplied excerpt

Positive & Negative Checks

GitHub reports success for the identity check, metadata-read step and negative-test step. The supplied excerpt reports AccessDeniedException for ListSecrets.

Review limit: The recorded negative-test script accepts any nonzero exit. A service, credential or syntax error can therefore pass that script; a stronger oracle must check the expected authorization error.

AREA 05 Author-published summary

CloudTrail Record

The repository document lists token exchange, secret retrieval, policy readback and denied enumeration events with timestamps and event IDs.

Review limit: The published table is a lookup aid. Raw events and integrity-validation evidence are needed for independent forensic verification. No post-quantum transport claim is established by the displayed records.

AREA 06 Source-inspected

Repository & Dependency Records

The repository includes ignore rules and a lock file selecting AWS provider 6.73.0 with checksums. The complete snapshot also includes variables and outputs.

Review limit: The HCL provider constraint remains >= 5.0. Actions use mutable @v4 tags and the runner uses ubuntu-latest. Ignore rules do not remove already tracked files or prior exposure.

AREA 07 Review criteria

Change History & Next Validation

Architecture, audit and patch records preserve the author’s deployment history. The website separates those records from independently checked run metadata.

Review limit: Next checks include effective permissions, rejected-source cases, another-secret reads, precise error classification and source/run provenance. Improvements require new execution evidence before being described as validated.

Recorded GitHub Actions Workflow

The workflow below is the file attached to the successful source revision. It includes role-duration-seconds: 3600 and does not contain the additional ::add-mask:: line shown in the earlier website rendering. Its JSON projection prints selected fields from the simulated payload.

Open the recorded workflow

.github/workflows/akcce-ota-oidc-attestation.yml — recorded source
name: AKCCE Zero-Trust AWS OIDC Attestation

on:
  push:
    branches: [ "main" ]
  workflow_dispatch:

permissions:
  id-token: write
  contents: read

jobs:
  oidc-ephemeral-sts-attestation:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Gate 1 & 2 - Exchange GitHub OIDC JWT for Ephemeral AWS STS Role
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::698250246230:role/akcce-autonomous-fleet-01-ota-oidc-role
          aws-region: us-east-2
          role-session-name: AKCCE-AutonomousFleet-OIDC-Proof
          role-duration-seconds: 3600

      - name: Verify Ephemeral STS Assumed-Role Identity
        run: |
          aws sts get-caller-identity --output json

      - name: Gate 3 & 4 Positive Proof - Scoped OTA Signing Key Metadata Read
        run: |
          SECRET_JSON=$(aws secretsmanager get-secret-value \
            --secret-id autonomy-prod/ota-firmware-signing-key \
            --region us-east-2 \
            --query SecretString \
            --output text)
          echo "$SECRET_JSON" | jq '{key_id, algorithm, fleet_domain, bound_repo_node_id, bound_owner_node_id, attestation_state}'

      - name: Kill-Chain Counter-Test - Prove Lateral Vault Enumeration is Denied
        run: |
          set +e
          OUT=$(aws secretsmanager list-secrets --region us-east-2 2>&1)
          RC=$?
          set -e
          echo "$OUT"
          if [ "$RC" -eq 0 ]; then
            echo "SECURITY_FAILURE: Lateral ListSecrets unexpectedly succeeded!"
            exit 1
          fi
          echo "AKCCE_COUNTER_TEST_PASSED: Lateral secretsmanager:ListSecrets deterministically blocked (exit $RC)."
Negative-test interpretation. The final step fails when listing succeeds, but treats every other exit as a pass. AWS CLI code 254 means a service returned an error; it is not specific to access denial. See the AWS CLI return-code reference. A revised test should distinguish the expected denial from unrelated failures and then be rerun.

Priority Improvements to Test Next

  • Strengthen the negative-test oracle: Require the expected authorization denial, fail on unrelated errors and preserve useful non-sensitive diagnostics.
  • Expand the access tests: Check unauthorized source claims, known adjacent-resource reads and unnecessary write or administration operations in a controlled environment.
  • Review effective permissions: Evaluate role, resource and other applicable policies. Design any exclusive-access requirement deliberately rather than inferring it from an Allow statement.
  • Improve reproducibility & recovery: Review immutable workflow dependencies, runner assumptions, state protection, secret recovery settings and deployment rollback.
  • Retain evidence for stronger claims: Store raw event exports and their validation results, identify the source revision for each run and test actual signing separately if it becomes part of the implementation.
