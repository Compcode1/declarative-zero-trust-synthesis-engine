[DESIGN EXPLANATION :: HUMAN-GOVERNED MACHINE IDENTITY ENGINEERING]

Tethered AI Systems Engineering

Structured assistance for discovery, reviewed configuration, access testing and operational evidence.

The System Directive is a reusable engineering protocol for working with an AI assistant on machine identity configurations.

  • Practical purpose: Make deployment context, trust assumptions, permissions, human decisions and validation results explicit. This helps produce work that an engineer can inspect and reproduce.
  • Three distinct responsibilities: The assistant proposes and explains; the engineer reviews and authorizes; execution tools and cloud services enforce configured access restrictions.
  • Scope of this page: The sections below describe design intent and required review practices. Actual support and security outcomes depend on the implementation and tests for each configuration.

What “Tethered” Means

Use the model’s speed inside an explicit review process. The directive supplies instructions and checkpoints; it becomes part of a technically controlled workflow when the surrounding tools implement scoped access, approval checks, persisted state and evidence collection.

[SECTION 01 :: WORKFLOW, AUTHORITY & EVIDENCE]

Anatomy of the Engineering Workflow

Three complementary layers help turn a deployment request into a reviewable change and an evidence record. Each layer has a distinct responsibility.

[LAYER 01 :: STRUCTURED ASSISTANCE]

The AI Co-Pilot

  • Discover before proposing: Draft read-only queries to identify the active cloud context, workload issuer, trust claims and target resource. Record the source and unresolved assumptions. Discovery results still need interpretation.
  • Make changes reviewable: Propose cloud-specific configuration, execution commands and expected results. Treat repository text, tool output and error messages as input data rather than authorization to change the task.
  • Declare execution capability: In advisory chat, the engineer runs commands. In a tool-enabled integration, available tools and credentials determine actual access; a prompt cannot revoke that access.
[LAYER 02 :: REVIEW PROTOCOL]

The System Directive

  • Organize seven phases: Structure intake, federation discovery, payload review, access testing, audit evidence, repository handoff and lessons learned. Human checkpoints identify the next approved action.
  • Keep the baseline visible: Review Boundary, Identity, Federation and Access together with the five guardrails below. Track pending inputs, exceptions and changes to the approved plan.
  • Persist state where needed: Chat labels and self-checks are procedural aids. A separate workflow service must store run state and validate transitions if machine-enforced gates are required.
[LAYER 03 :: IMPLEMENTATION & RESULTS]

The Control and Evidence Layer

  • Enforce at execution: Use scoped cloud identities, protected repositories, policy checks and approvals on the execution path. Bind approval to the reviewed artifact and require a new review when it changes.
  • Test specific boundaries: Run an intended operation and meaningful denied cases. Distinguish authentication failure, authorization denial, network error and missing resource.
  • Retain attributable records: Link the baseline, deployed revision, run output, identity, resource and time window. Markdown summaries support review; they are editable records unless separate integrity controls are implemented.

Where “tethering” becomes enforceable: The directive communicates the rules. Authorization checks in the execution tools and cloud services enforce them. A chat response saying [STRICT HALT] is a request to pause, not an independent technical barrier.
[SECTION 02 :: COMPLEXITY & VALIDATION]

Reduce Ambiguity. Measure the Result.

Machine identity configuration spans trust, permissions, deployment state and runtime behavior. The workflow makes those dependencies explicit so engineers can review and test them systematically.

[CONTROL 01 :: DEFINE THE BUILD]

Lock the Scope

  • Five intake coordinates: Identify the cloud boundary, target resource, execution agent, existing or new infrastructure, and deployment tool. Add an accountable owner, environment and recovery plan.
  • Cloud-specific branches: AWS, Entra ID/Azure and Google Cloud have different policy models, claim handling, limits and logging. Shared workflow structure does not establish equivalent implementation or tested coverage.
  • Show supported coverage: Describe combinations as planned, implemented or tested, with links to matching artifacts. A product of option counts is not evidence that every combination works.
[CONTROL 02 :: CHECK ASSUMPTIONS]

Use Observable Inputs

  • Resolve real context: Read identifiers from authorized APIs and verify the active account and intended environment. Never invent deployment coordinates. Keep secret values out of shared transcripts.
  • Review trust end to end: Compare the actual issuer, audience and subject against the relying party’s policy. Review who can change the source repository, workflow, environment or service account that supplies those claims.
  • Recheck after changes: A successful lookup captures a point in time. Reassess dependencies, effective permissions and the proposed plan when the environment changes.
[CONTROL 03 :: BOUND THE REPAIR LOOP]

Diagnose with Evidence

  • One defect, one hypothesis: Record the error, affected artifact, proposed cause, test and result. Preserve the last reviewed baseline and inspect each change before execution.
  • Use a review budget: The original fourth-iteration halt is a chosen operating policy. Stop earlier for destructive changes, privilege expansion or evidence that contradicts the hypothesis.
  • Maintain tested lessons: Review fixes before changing the directive or templates. Version the result, test regressions, and revise or retire obsolete rules. A longer prompt does not establish better security.

Evaluate improvement against a defined baseline

Compare the directive with a documented baseline workflow on the same representative tasks, model versions, tool permissions and review criteria. Repeat trials and report sample size, task difficulty and uncertainty.

  • Configuration quality: Measure incorrect trust claims, excessive grants, unintended plan changes and defects missed by review. Include safe failure when required inputs are absent.
  • Boundary behavior: Count expected allow and deny outcomes separately. Verify the denial reason; an unavailable endpoint or invalid credential does not prove least privilege.
  • Operational usefulness: Track completion time, human review effort, diagnostic attempts and evidence completeness. Separate a working deployment from an independently reviewed security outcome.
No measured reliability percentage is claimed here. The earlier 0.85¹⁰ ≈ 19.7% example assumes ten independent steps with an identical, unmeasured success probability. The arithmetic cannot establish this workflow’s reliability. Verifying inputs also does not make downstream configuration, review or tests infallible.
[SECTION 03 :: RESEARCH & RISK GUIDANCE]

Four Practices Informing the Design

These references inform engineering choices. They include research, a security risk taxonomy and risk-management guidance; citing them does not certify this implementation or validate every design choice.

[PRACTICE 01 :: EXTERNAL OBSERVATIONS]

1. Evidence-Grounded Iteration

Use observations to check assumptions and update a proposed action. External data can improve an answer while remaining incomplete, stale or misinterpreted.

Application to this workflow
  • Discovery: Request targeted read-only API queries and explain which fact each output establishes. Distinguish observed values from inferred conclusions.
  • Troubleshooting: Summarize the hypothesis, supporting observations, uncertainty and next test. Preserve enough context for a reviewer to evaluate the change.
Source and scopeReAct: Synergizing Reasoning and Acting in Language Models

Yao et al. study interleaved reasoning and actions on specified benchmarks. Those results support exploration of observation-driven workflows; they do not prove that CLI lookups eliminate hallucination in cloud deployments.

[PRACTICE 02 :: EXECUTION AUTHORITY]

2. Bounded Permissions and Autonomy

Restrict the functions and permissions available to an assistant. Place authorization checks on each execution path and require appropriate approval for consequential changes.

Application to this workflow
  • Advisory mode: Keep cloud execution with the engineer when using the directive as a chat prompt. Review generated commands before running them.
  • Tool-enabled mode: Use narrowly scoped tools and credentials, independently checked requests, recorded approvals and monitored execution. Avoid granting open-ended administrative access to resolve a failed operation.
Source and scopeOWASP LLM06:2025 — Excessive Agency

OWASP describes risks from excessive functionality, permissions and autonomy. Its mitigation guidance places authorization in tools or downstream services. The earlier LLM08 label refers to the older 2023–24 edition.

[PRACTICE 03 :: ACCOUNTABLE REVIEW]

3. Human Roles and Risk-Based Gates

Define who owns the identity, who reviews changes, who can execute them and who can accept an exception. Give the reviewer concrete evidence and a specific decision.

Application to this workflow
  • Before execution: Review target context, trust policy, effective permissions, proposed changes and recovery options. Identify any exception owner, scope and expiration.
  • During operation: Record decisions and unresolved findings. Adjust approval depth to the change’s impact and the organization’s policy rather than assuming every action needs the same ceremony.
Source and scopeNIST AI RMF 1.0 — Appendix C

NIST discusses explicit human–AI roles and responsibilities across different degrees of autonomy. This is risk-management guidance, not a universal requirement to approve every chat step, and this page makes no certification claim.

[PRACTICE 04 :: DIAGNOSTICS & LEARNING]

4. Bounded Troubleshooting

Use limited, observable experiments and escalate when the next attempt is no longer justified. Retain the result so future changes can be tested against it.

Application to this workflow
  • Escalation: A failed-attempt budget can prompt reassessment. Review error changes, alternative causes, blast radius and recovery rather than inventing a numerical probability of success.
  • Learning: Track verified fixes and failed assumptions. Test directive and template revisions against prior defects, including cases where the correct response is to stop.
Source and scopeA Survey on Hallucination in Large Language Models — Huang et al.

The survey reviews causes, detection, mitigation and unresolved limitations. It is context for validation work, not evidence that a fourth-iteration halt is optimal or that a prompt can guarantee permanent self-correction.

1. Replication and Readiness

  • Failure mode: A newly created identity or policy may not yet be usable by a dependent API. Confirm the actual error and resource context before retrying.
  • Review approach: Use supported readiness checks, bounded retries and backoff, with a clear timeout. A fixed 30-second delay is an environment-specific workaround, not a replication guarantee.

2. Claims and Policy Limits

  • Failure mode: An unexpected issuer, audience, subject format, case or policy size can break the intended exchange. Claim formats and policy limits vary by cloud and workload source.
  • Review approach: Inspect actual claims and the applicable provider schema. Review repository and environment protections. Choose network ranges and partitioning against documented limits; a universal 90-subnet rule can omit required coverage.

3. Authorization and Log Delays

  • Failure mode: Policy propagation and log ingestion can delay observations. Missing MFA context, authorization and network errors need separate diagnoses.
  • Review approach: Read back policy, test the intended operation and retain attributable logs when available. Metrics are supporting signals. Use an approved authentication flow; do not assume the portal or device code universally fixes an authorization failure.
