Once all checks pass, Step 6 generates the 100% finished code, blueprint ledger, and live cloud proof, while Step 7 enforces a 3-strike circuit breaker if any error occurs.

[LAYER 1: AI SYSTEMS ENGINEERING STANDARDS]
The 4 Core Rules of the System Directive

Why use formal AI Systems Engineering in cybersecurity? Because raw, untethered AI is a guessing engine—if you ask it to write a cloud security script without strict boundaries, it will guess missing IDs, use outdated commands, or grant dangerous administrative permissions just to make an error go away. To use AI safely in a security role, I built the master System Directive around four global AI engineering standards. Below is what each standard means in the industry, and how it actually works at the keyboard inside my machine.

1. Agentic Patterns (ReAct)
The Industry Standard (ReAct Framework) Alternating between reasoning and taking action so the AI checks real external data instead of guessing in a vacuum.
How It Works in My System Directive In Steps 1–5, the AI is forbidden from guessing Azure or GitHub names. Instead, it gives me terminal lookup commands, waits for me to paste back the real console output, and only generates code using verified live IDs.
2. Bounded Autonomy (OWASP LLM08)
The Industry Standard (OWASP LLM08: Excessive Agency) Preventing an AI model from having unchecked permissions or running destructive commands on its own.
How It Works in My System Directive The AI has zero direct access to my cloud account. It is trapped inside strict rules that force read-only lookups (data/existing) for Brownfield resources and single-vault data permissions (never Owner or Contributor).
3. Human-in-the-Loop Governance (NIST)
The Industry Standard (NIST AI Risk Management) Keeping a human engineer in control of risk decisions with clear accountability at every critical step.
How It Works in My System Directive The AI cannot skip ahead or dump code prematurely. It must pause at each step—Boundary, Identity, OIDC Trust, and Vault Permissions—until I verify the terminal output and approve moving forward.
4. Cognitive Circuit Breaking
The Industry Standard (Hallucination Prevention) Stopping AI models from drifting into false, repetitive guessing loops when a long conversation hits an error.
How It Works in My System Directive Enforces the 3-Strike Rule in Step 7: if a script fails 3 times in a row, Attempt #4 triggers a hard stop that forbids the AI from writing code until we diagnose the root cause and log it in the Defect & Patch Ledger.

[LAYER 2: THE 5 BUILT-IN SAFETY LOCKS]
Enterprise Guardrails

To make the four AI engineering standards above work in real life, the System Directive enforces five specific safety locks during every build. These locks stop the five most common mistakes that ruin cloud deployments: leaking passwords, deleting existing company vaults, granting overly broad admin rights, downloading unverified code plugins, and exposing tokens in pipeline logs.

Secret & Credential Protection Routing IDs Go In; Secrets Stay Out. Non-secret address IDs (Tenant, Subscription, Repo) are pasted into the chat so the AI writes finished code, while passwords are eliminated via OIDC and any personal token (PAT) is typed invisibly in the terminal (read -s).
Existing Asset Protection Never Wipe Out Live Resources. Forces read-only lookups (data blocks in Terraform or existing in Bicep) when connecting to Brownfield environments, and requires a deletion lock (prevent_destroy) on new Greenfield builds.
The Contributor Trap No Master Keys Allowed. Blocks broad management roles like Owner or Contributor that could let a pipeline delete cloud resources. Assigns only data-level access locked to one specific vault or database ID.
Pinned Provider Versions Supply Chain Safety. Requires every Terraform or Bicep script to lock in exact, verified Microsoft provider version numbers so an unverified or broken third-party update never sneaks into the build.
Log Token Masking Hiding Tokens in Pipeline Logs. Forces pipeline scripts to mask sensitive values in memory (such as ::add-mask::) so temporary 60-minute tokens or vault secrets never print out in plain text on a log screen.

[LAYER 3: WHO DOES WHAT]
The Execution Triad

Inside the Zero Trust Interactive State Machine, the work is divided cleanly among three distinct roles. By separating The Architect (who runs terminal commands and approves each step), The State Machine (the hard-coded rules inside the System Directive), and The AI Engine (which writes the code once all IDs are verified), the AI can never run off on its own.

The Architect The Human Engineer at the Keyboard. Selects the 5 build options, runs lookup commands in the local terminal, pastes verified non-secret routing IDs into the chat, approves each step, and runs the final code in Azure.
The State Machine The Rules Inside the System Directive. The strict checklist that forces the AI to go one step at a time, blocks passwords and wildcards, enforces read-only Brownfield lookups, and pulls the 3-strike circuit breaker if errors occur.
The AI Engine The Tethered Code Generator. Provides the exact terminal lookup commands during Steps 1–5, locks verified IDs and safety rules into memory, and writes the 100% finished IaC code and ledgers in Step 6.

The 4 Core Verification Gates (Steps 2–5)

After selecting the 5 build options in Step 1, the machine steps through four verification gates in the chat. No code files or ledgers are output during these four gates—instead, The Architect and The AI Engine verify the real cloud IDs and lock in the security settings for each layer before moving to the next.

Gate 1: Boundary (Step 2) Verify Cloud Location & Safety Mode. Confirms the exact Entra ID Tenant ID, Azure Subscription ID, and Resource Group name, and locks in read-only lookup mode (Brownfield) or deletion protection (Greenfield).
Gate 2: Identity (Step 3) Machine Identity Setup. Looks up or creates the non-human App Registration and Service Principal in Entra ID, locking it to Single-Tenant only (AzureADMyOrg) and disabling all web browser logins (redirect_uris = []).
Gate 3: Federation (Step 4) Passwordless OIDC Trust. Pulls the exact repository and branch strings from the terminal to enforce a letter-for-letter Subject Claim match with zero * wildcards, a 60-minute token limit, and a built-in server sync pause timer.
Gate 4: Access (Step 5) Single-Vault Permission & MFA Safe Path. Blocks Owner and Contributor roles, locking a data-only role strictly to the single target Key Vault, Storage Account, or Cosmos DB—and separating the role step if terminal MFA blocks it.

Step 7: The 3-Strike Circuit Breaker & Prompt Upgrades

Even with careful planning, real-world cloud deployments can hit unexpected errors—like a Microsoft API quirk, a missing permission, or a timing bug. When a script fails with an untethered AI, the AI usually apologizes, guesses a random fix, and breaks two other things in an endless loop. To stop that, the Zero Trust Interactive State Machine uses a structured 4-part troubleshooting loop that stops AI guessing on Attempt #4 and turns every solved bug into a permanent upgrade to the master System Directive.

1. Counting Every Fix Attempt (Attempts 1–3) When a terminal command returns an error, the AI switches into strict diagnostic mode. It reads the exact terminal error message and is allowed up to 3 focused attempts to fix the specific line of code under The Architect's supervision without changing unrelated parts of the script.
2. The 3-Strike Circuit Breaker (Attempt #4 Halt) If the error is still not solved by Attempt #4, the Circuit Breaker trips automatically. The State Machine strictly forbids the AI from generating any more code. Instead, the AI must stop, summarize what failed across the 3 attempts, and wait for The Architect to inspect the root cause and direct the next move.
3. The Defect & Patch Ledger (DPL) Once The Architect and the AI isolate the real cause of the bug, the fix is tested locally in the terminal until it passes 100%. Only after live proof of success is the bug's root cause and exact solution recorded inside the Defect & Patch Ledger (DPL).
4. Upgrading the Master System Directive At the end of the session, every proven fix logged in the DPL is written directly into the master System Directive prompt (for example, adding the 30-second sync pause timer or handling terminal MFA blocks). That way, the assembly line permanently learns from every real-world bug and never repeats the same mistake.
Industry AI Classification
L4 Agentic Architecture under Strict Engineer-Guided (HITL) Governance

How does the Zero Trust Interactive State Machine fit into standard AI industry classifications? Rather than letting an AI act as an unchecked autonomous agent—or relying on casual "vibe coding" prompts—this system uses formal AI Systems Engineering best practices to harness the speed of an AI code generator inside a strict, human-controlled assembly line. Here is what the three engineering pillars behind this classification mean in plain English:

Applied Control Theory (Brakes & Steering)

In engineering, "control theory" simply means putting reliable brakes and steering on a powerful engine so it stays on the road. By requiring human approval at every step (Steps 1–5) and enforcing a hard 3-strike Circuit Breaker on Attempt #4 (Step 7), the System Directive gives the Architect complete steering and emergency brakes over the AI.

High-Assurance Verification (Before & After Proof)

In cybersecurity, a script finishing without an error message is not enough—you have to prove the cloud settings are actually secure. This system produces both a "Before" blueprint (the Identity Architecture Ledger) and an "After" live cloud check (the Audit Results Ledger and KQL Log Proof) to verify that the deployment works with zero passwords and zero 403 Forbidden errors.

Continuous Rulebook Evolution (Learning From Bugs)

Instead of solving a cloud error once and forgetting about it, every bug caught by the 3-strike Circuit Breaker is diagnosed, proven in the terminal, logged in the Defect & Patch Ledger, and added into the master System Directive. Over 28+ iterations, this process turned real-world cloud errors into a rock-solid, repeatable rulebook.
