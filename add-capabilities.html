Day-2 Multi-Cloud Modules

Extend a machine identity baseline through reviewed, cloud-specific controls and explicit validation.

Day-2 security work connects each proposed restriction to its prerequisites, expected behavior, evidence and operational owner.

  • Start from current facts: Refresh identity, trust and effective-access observations before expanding a prior deployment. Reuse records deliberately rather than skipping discovery automatically.
  • Review the impact: A new policy can reduce access, introduce an exception or interrupt a workload. Additive code does not guarantee a non-disruptive change.
  • Separate design from proof: The Entra example below is based on a supplied case narrative. Cross-cloud controls are extension areas, and reported outcomes are distinguished from independently assessable evidence.

[STEP 1]

Refresh the Identity Baseline

Day-2 work starts from the current environment. Reuse prior discovery only after checking that the identity, trust, grants and operational assumptions remain valid.

Identity, trust and access

  • Confirm the target: Distinguish application client ID, application object ID and service-principal object ID. Link observations to a run, configuration revision and UTC timestamp.
  • Review the trust source: Read the actual issuer, audience and subject conditions and inspect who can modify the repository, workflow, environment or service account supplying the assertion.
  • Review effective permissions: Check direct, inherited and resource-based grants, alternate credentials and administrative mutation paths. Keep deployment privileges separate from runtime access.

Policy prerequisites and recovery

  • Supported scope: Entra workload Conditional Access targets eligible single-tenant service principals and requires Workload ID Premium for policy creation/modification. Managed identities are excluded.
  • Change authority: Use an approved administrative authentication flow. Portal use and device-code login do not universally guarantee that authorization requirements are satisfied.
  • Recovery: Identify owners, approved exceptions, rollback criteria and persistent state. An added policy can interrupt a working service even if no resource is deleted.

It also assumes a fixed replication delay and token lifetime. Treat those as environment-specific items to verify, not universal prerequisites.

[STEP 2]

Design the Location and Risk Policies

Define the condition each control is intended to enforce, its target and state, and the observations that would demonstrate its behavior.

Module A · Location-Based Policy

  • Intended behavior: Restrict token requests for the selected service principal according to the configured location conditions. A shared runner IP range is a network attribute, not proof of repository ownership.
  • Range handling: Review the complete intended egress set, IPv4/IPv6 behavior, named-location limits and refresh process. Partitioning must preserve coverage; a fixed 90-range rule is not a universal limit.
  • Validation: Retain a fresh allowed-origin request and an approved outside-origin test, including the policy state, target principal and sign-in evaluation. A generic workflow failure is not enough.

Module B · Service-Principal Risk Policy

  • Intended behavior: Use the configured service-principal risk condition to block applicable token requests. This is a different condition from human user or sign-in risk.
  • Detection limits: Workload detections include offline signals and can depend on learned behavior. Detection and access-control scope differ. A successful request does not establish that all replay or compromise would be detected.
  • Validation: Review policy targeting and risk evaluation. Use an approved, isolated test method if exercising risky-state behavior; do not create a real leak or compromise to demonstrate a policy.

Risk capability and limits: Entra workload identity risk documentation ↗.

Token policy is not universal connection termination. Do not infer that these settings inspect every Key Vault API call, immediately invalidate every issued credential, or detect every replay. Any continuous enforcement has separate client/resource requirements that are not demonstrated in this case.

[STEP 3]

Diagnose the Schema Failure

The source reports an HTTP 400 during policy creation and a successful retry. That supports a troubleshooting account; the full request and structured response are needed to establish the exact cause.

Inspect the failing request

  • Isolate the operation: Record the endpoint/version, sanitized JSON, response body, request identifier and time. HTTP 400 alone does not identify which field failed.
  • Check the native model: Compare Graph property names and types with the selected API schema. Terraform provider fields and native JSON are separate interfaces.
  • Review the complete change: Show the unified artifact and its diff. Reprinting a whole file can aid review, but does not validate it or authorize execution.

Verify before codifying

  • Stage the hypothesis: Record the proposed cause and repair before testing. Mark the fix verified only after the relevant response, read-back and behavioral result are captured.
  • Reassess retries: A fourth-iteration halt is a chosen operating rule, not proof of safety. Stop earlier for scope expansion or damaging changes, and explain uncertainty without invented probabilities.
  • Release a tested lesson: Version directive/template changes, test prior defects and allow obsolete rules to be revised. Do not promise that a prompt update makes an error impossible to repeat.

[STEP 4]

Verify Behavior and Record the Outcome

Separate an observed functional path from a demonstrated security boundary. Complete the assessment only to the extent supported by evidence.

Immediate execution evidence

  • Record outcomes: Capture identity, target, requested operation, actual status and the executed revision. Avoid printing tokens or secret contents.
  • Exercise relevant boundaries: Separate allowed access, trust rejection, location-policy denial and ordinary authentication/network failures. Keep approvals and recovery criteria for each test.
  • Track the policy state: Report-only, enabled, disabled and deleted are different states. Removing a policy may restore functionality but removes the restriction it supplied.

Policy and service evidence

  • Confirm evaluation: Review service-principal sign-in policy evaluation alongside the requested resource operation. A metric spike cannot establish risk level, policy applicability or caller attribution.
  • Allow asynchronous collection: Wait for required observations or mark them pending. Collection, ingestion and query availability vary; a query file is not an executed query result.
  • Close with ownership: Record findings, accepted exceptions, final policy state, monitoring and recovery owners. An editable ledger is not an immutable or automatically compliant audit receipt.
