[MASTER SYSTEM DIRECTIVE SPECIFICATION :: v9.1]

DETERMINISTIC AI SYSTEMS ENGINEERING

Generative AI is naturally a probabilistic engine—it predicts words based on patterns—whereas cloud Identity and Access Management (IAM) requires exact, binary precision: an OIDC subject string or vault permission either matches 100%, or the deployment fails. To bridge that gap, I took a probabilistic AI engine and tethered it to a master System Directive to make it deterministic. This page documents how the Zero Trust Interactive State Machine uses established AI Systems Engineering best practices to guide every build from Step 1 through Step 7.

Architectural Insight: Why We Treat the System Directive Like a Compiler
"A traditional code compiler takes human instructions, checks that every variable and rule is valid, and refuses to build the program if anything is missing. The Zero Trust Interactive State Machine works the exact same way: in Steps 1 through 5, the System Directive forces the AI to check every Azure ID, repository string, and security lock with the Architect in the chat before it is allowed to output a single line of deployment code in Step 6."

[SECTION 01 :: HOW THE SYSTEM DIRECTIVE IS STRUCTURED]

Anatomy of the Zero Trust Interactive State Machine

Instead of using a short, open-ended prompt, the Zero Trust Interactive State Machine (v9.1) is driven by a structured master System Directive divided into three layers: the tethered AI code generator, the 7-step rulebook, and the "Before" and "After" verification ledgers.

[LAYER 01 : THE AI ENGINE]

The Tethered Code Builder

The AI Engine has zero direct access to the cloud and cannot act on its own. During Steps 1–5, it provides terminal lookup commands and saves verified Azure and pipeline IDs into memory. Only in Step 6 does it generate the 100% finished Terraform, Azure Bicep, or PowerShell REST API code across any of the 72 build combinations.

[LAYER 02 : THE STATE MACHINE]

7 Steps & 32 Hard Rules

The State Machine is the master rulebook inside the System Directive: 7 sequential steps governed by 32 strict rules. It forces the AI to pause at every gate for human approval and uses XML-fenced blocks (<PASSIVE_UI_STRING_LITERALS>) so menu labels and display text never confuse the AI's code generation rules.

[LAYER 03 : BUILT-IN VERIFICATION]

Before & After Audit Ledgers

Rather than treating security audits as an afterthought, Step 6 and Step 7 automatically generate four verification records: the "Before" blueprint (Identity Architecture Ledger), the "After" live cloud check (Audit Results Ledger), live KQL Log Queries, and the Defect & Patch Ledger (DPL).

[SECTION 02 :: WHY THIS ARCHITECTURE EXISTS]

Solving the Speed vs. Precision Challenge in Cloud IAM

In modern cloud security, engineers need to deploy passwordless identities quickly—but cloud identity configurations require exact precision across dozens of moving parts (4 CI/CD platforms, Brownfield vs. Greenfield states, 3 target vaults/databases, and 3 IaC languages). If a single repo capital letter, tenant ID, or role scope is off, the deployment either fails with a 403 Forbidden error or leaves a security gap. By tethering the AI to a step-by-step State Machine, we get the speed of AI code generation while guaranteeing every setting is verified against the live cloud first.

[OBJECTIVE 01 : FAST, REPEATABLE BUILDS]

Rapid Passwordless OIDC Setup

Uses the speed of The AI Engine to quickly assemble complete OpenID Connect (OIDC) passwordless login pipelines and network-restricted Conditional Access policies without writing boilerplate syntax from scratch.

[OBJECTIVE 02 : ZERO AI GUESSWORK]

100% Verified Cloud IDs

Replaces AI guessing with real terminal lookups in Steps 1–5. Every generated script is locked to verified Azure IDs, single-vault data roles, pinned provider versions, and Brownfield/Greenfield protection rules.

[OBJECTIVE 03 : 72 BUILD COMBINATIONS]

Adapting to Any Stack

Automatically adjusts the OIDC subject claim format, single-asset RBAC role, and code syntax across 4 execution agents, 2 infrastructure states, 3 data-plane targets, and 3 IaC languages—keeping the exact same security standard across all 72 combinations.

[SECTION 03 :: AI SYSTEMS ENGINEERING STANDARDS IN ACTION]

The Four Pillars of the System Directive

To turn a probabilistic language model into a reliable engineering tool, the master System Directive (v9.1) is built directly on four globally recognized AI Systems Engineering standards. Here is what each standard means, how it works at the keyboard, and the research behind it.

[PILLAR 01 :: TERMINAL VERIFICATION & BUG LOGGING]

1. ReAct Loops & The Defect Ledger

Asking an AI to write a whole cloud script in one shot ("zero-shot prompting") forces the AI to guess missing environment details. Based on the ReAct (Reasoning and Acting) standard, our assembly line alternates between reasoning in the chat and running real lookup commands in the terminal.
How It Works in the System Directive (Steps 1–5 & Step 7)

In Steps 1–5, The AI Engine gives The Architect terminal commands to pull real IDs before writing any code. And in Step 7, if a script hits an error, the AI enters a focused Generate-Validate-Fix loop: once the fix is proven in the terminal, Rule 15 logs the root cause in the Defect & Patch Ledger (DPL) and Rule 9 outputs the entire, complete IaC file from top to bottom so partial code snippets never corrupt the build.

Reference Standard
ReAct: Synergizing Reasoning and Acting in Language Models (Yao et al.)

Foundational research from Princeton and Google Brain showing that AI models stop hallucinating when forced to alternate between reasoning steps and checking real external data.

[PILLAR 02 :: PERMISSION & MFA SAFETY LOCKS]

2. Bounded Autonomy & MFA Safe Execution

When an untethered AI hits an "Access Denied" or MFA error during a deployment, it often tries to bypass the error by granting broad admin roles or overwriting resources. We apply OWASP LLM08 (Excessive Agency) to lock the AI inside strict permission boundaries.
How It Works in the System Directive (Step 2 & Step 5)

The State Machine forbids management roles (Owner / Contributor), enforces Brownfield read-only lookups (data / existing), and applies Rule 29 (MFA Safe Execution) in Step 5: when an Azure security policy requires an interactive MFA popup to assign a role—which causes local terminal scripts to fail—the AI separates the role step from the script so the Identity and OIDC trust deploy cleanly, and guides The Architect to finish the role click in the Azure web portal.

Reference Standard
OWASP Top 10 for LLM Applications (LLM08: Excessive Agency)

The global application security standard for preventing AI models from having unchecked permissions or running destructive commands across enterprise systems.

[PILLAR 03 :: STEP-BY-STEP HUMAN APPROVAL]

3. Human-in-the-Loop (HITL) Governance

In enterprise security, a human engineer must remain accountable for every change made to the cloud directory. Following the NIST AI Risk Management Framework, the assembly line requires explicit approval from The Architect at every single step.
How It Works in the System Directive (Steps 1–6)

Rule 1 (The Step-by-Step Halt Rule) forbids the AI from combining multiple steps or dumping code early. The AI must pause at each gate—Boundary (Step 2), Identity (Step 3), OIDC Trust (Step 4), and Vault Permissions (Step 5)—echo back the verified IDs, list the exact files it plans to generate in Step 6 (Rule 12), and wait for The Architect to approve before moving forward.

Reference Standard
NIST Artificial Intelligence Risk Management Framework (AI RMF 1.0)

The U.S. federal standard establishing the "Govern" function—requiring clear human oversight, risk control, and human accountability for high-impact AI systems.

[PILLAR 04 :: STOPPING ENDLESS AI GUESSING LOOPS]

4. The 3-Strike Circuit Breaker

When a script fails repeatedly in a long chat session, AI models naturally lose track of earlier rules and start guessing in circles ("hallucination spirals"). We built a hard 3-Strike Circuit Breaker into Step 7 to stop the AI before it can dig a deeper hole.
How It Works in the System Directive (Step 7)

Before every reply, Directive 07 (The Self-Check Rule) forces the AI to verify it hasn't drifted off the System Directive. During troubleshooting in Step 7, the AI gets up to 3 tries to fix a terminal error. If the error still isn't solved on Attempt #4, the Circuit Breaker trips automatically: it forbids the AI from writing any more code, forces a plain summary of what failed across the 3 tries, and hands control back to The Architect.

Reference Standard
A Survey on Hallucination in Large Language Models (Huang et al.)

Research documenting how language models drift and repeat false guesses during long troubleshooting conversations—proving the need for hard attempt limits.

1. Preventing Microsoft Server Sync Crashes

The Bug: When a script creates a new identity or Named Location in Entra ID and immediately tries to attach an OIDC rule or Conditional Access policy a split-second later, Microsoft's servers haven't finished syncing yet and the script crashes.
The Built-In Fix: The System Directive automatically builds a 30-second pause timer (time_sleep in Terraform or Start-Sleep in PowerShell) between creation and attachment so Microsoft's directory catches up cleanly.

2. Preventing Casing Bugs & IP List Overflows

The Bug: Entra ID rejects OIDC logins (error AADSTS700213) if a single upper- or lower-case letter in the repo name doesn't match, and crashes if you feed thousands of GitHub runner IP addresses into one Conditional Access location block.
The Built-In Fix: Step 4 locks in exact letter-for-letter repo casing (e.g., Compcode1) via terminal lookup, and automatically splits large IPv4 lists into safe chunks using chunklist().

3. Beating Azure Portal Caching Delays

The Bug: When you toggle a setting or Conditional Access policy in the Azure web portal, the browser screen often shows old cached data for several minutes—causing pipeline tests to fail if you run them too early.
The Built-In Fix: Before running a live pipeline test, the System Directive requires a quick terminal audit command that queries the live Microsoft Graph API directly to confirm the new setting is 100% active across the directory.
